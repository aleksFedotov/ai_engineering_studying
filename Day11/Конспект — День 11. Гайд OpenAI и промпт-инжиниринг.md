## Часть 1. Классический гайд OpenAI: шесть стратегий (2023)

Классическая версия гайда (опубликована в декабре 2023) построена вокруг шести стратегий. Они не взаимоисключающие — комбинируются для усиления эффекта.

### Стратегия 1. Write clear instructions — пишите чёткие инструкции

Модель не умеет читать мысли: чем меньше ей приходится угадывать, тем ближе ответ к желаемому.

Тактики:
- включать детали в запрос для релевантного ответа;
- просить модель принять роль (persona);
- использовать разделители для обозначения частей ввода;
- указывать шаги, необходимые для выполнения задачи;
- приводить примеры;
- указывать желаемую длину ответа.

💡 **Вывод:** ключевая ментальная модель всего промптинга — «что здесь модель вынуждена угадывать?» (роль, формат, длину, аудиторию). Каждый приём гайда сводится к снятию этой неопределённости.

### Стратегия 2. Provide reference text — давайте опорный текст

Модели уверенно выдумывают ответы, особенно про эзотерические темы и цитаты. Опорный текст — как шпаргалка на экзамене: с ней меньше фабрикаций.

Тактики:
- инструктировать модель отвечать, используя опорный текст;
- инструктировать модель отвечать с цитатами из опорного текста.

💡 **Вывод:** требование цитат — механизм заземления (grounding): модель, сославшаяся на конкретный фрагмент, не может ответить «из головы». Это зародыш RAG.

### Стратегия 3. Split complex tasks into simpler subtasks — делите сложные задачи

Как в разработке ПО: сложную систему делят на модули. У сложных задач выше частота ошибок; задачу можно переопределить как конвейер, где выходы ранних этапов — входы следующих.

Тактики:
- классификация намерения (intent classification) для выбора релевантных инструкций;
- для длинных диалогов — суммаризация или фильтрация предыдущего диалога;
- рекурсивная суммаризация длинных документов по частям (map-reduce).

💡 **Вывод:** самая «инженерная» стратегия — про архитектуру, а не формулировки. Рекурсивная суммаризация и роутинг по интентам до сих пор лежат в основе агентных систем.

### Стратегия 4. Give the model time to "think" — дайте модели время «подумать»

Модель ошибается, когда отвечает сразу (как человек, считающий 17 × 28 в уме). Цепочка рассуждений перед ответом повышает надёжность.

Тактики:
- сначала собственное решение модели, потом вывод;
- «внутренний монолог» или последовательность запросов, чтобы скрыть рассуждения от пользователя;
- спросить модель, не упустила ли она чего-то на предыдущих проходах.

💡 **Вывод:** исторически важная стратегия, но сильно изменившаяся: в reasoning-моделях цепочка рассуждений встроена, явно просить «распиши ход мыслей» уже не нужно. Тактика «сначала своё решение, потом сравнение» остаётся рабочим приёмом самопроверки.

### Стратегия 5. Use external tools — используйте внешние инструменты

Компенсируйте слабости модели другими инструментами: RAG подскажет документы, исполнение кода — точную математику. Если инструмент решает задачу надёжнее — отдайте её инструменту.

Тактики:
- поиск на эмбеддингах для извлечения знаний;
- исполнение кода для точных вычислений и вызова внешних API;
- доступ к конкретным функциям (function calling).

💡 **Вывод:** принцип «не заставляй модель делать то, что надёжнее делает инструмент» недооценён. LLM — интерфейс рассуждения и оркестрации, а не универсальный вычислитель.

### Стратегия 6. Test changes systematically — тестируйте изменения системно

Улучшение проще, если его можно измерить. Правка может улучшить результат на отдельных примерах, но ухудшить на репрезентативной выборке — нужен набор тестов (eval).

Тактика:
- оценивать выводы модели относительно эталонных («gold-standard») ответов.

💡 **Вывод:** это то, что отличает промпт-инжиниринг от «подбора заклинаний». Даже примитивный eval из 20–30 примеров радикально меняет качество итераций.

## Часть 2. Актуальная версия гайда (Responses API, эпоха GPT-5)

Страница гайда переписана: вместо «стратегий формулировок» — инженерное руководство по работе с моделью через API.

### 2.1. Базовая механика

- Модель вызывается через Responses API: параметры `model`, `input`, ответ читается через `output_text`.
- Массив `output` часто содержит больше одного элемента (вызовы инструментов, reasoning-данные) — нельзя полагаться на `output[0].content[0].text`.
- Структурированный вывод в JSON — функция Structured Outputs.

### 2.2. Выбор модели — первая «настройка» промпта

- **Reasoning-модели** — внутренняя цепочка рассуждений, сильны в сложных задачах и планировании, медленнее и дороже.
- **GPT-модели** — быстрые и дешёвые, требуют явных инструкций.
- **Большие vs маленькие (mini/nano)** — компромисс скорость/цена/интеллект.

💡 **Вывод:** промпт и модель — одна система. Итерации по промпту делать на той модели, которая пойдёт в продакшен.

### 2.3. Главные правила игры

Определение: промпт-инжиниринг — написание инструкций, чтобы модель **стабильно** генерировала нужный контент. Два обязательных правила, которых не было в 2023-м:

1. **Пиноваться к снапшотам моделей** (например, `gpt-4.1-2025-04-14`) — даже снапшоты одного семейства ведут себя по-разному.
2. **Строить тесты и eval-наборы** перед правками промптов и сменой версий.

### 2.4. Роли сообщений и приоритеты

Инструкции передаются параметром `instructions` или сообщением с ролью `developer` (эквивалентно).

| Роль | Кто пишет | Приоритет |
|---|---|---|
| `developer` | разработчик приложения | высший |
| `user` | конечный пользователь | ниже developer |
| `assistant` | модель | — |

Метафора: developer-сообщение = определение функции (правила, бизнес-логика), user-сообщение = аргументы.

Подводный камень: `instructions` действует только на текущий запрос; при ведении диалога через `previous_response_id` инструкции прошлых ходов не сохраняются в контексте.

💡 **Вывод:** иерархия ролей — ещё и инструмент безопасности (пользователь не перебивает правила разработчика). Постоянные правила надёжнее держать в developer-сообщении или передавать `instructions` каждый раз.

### 2.5. «Промпты — это код»

- Продакшен-промпты хранить в коде приложения; переиспользуемые prompt-объекты упраздняются (сворачивание с июня 2026, отключение `v1/prompts` — ноябрь 2026).
- Сборщики промптов — в маленьком модуле рядом с фичей; типизированные аргументы для динамических данных.
- Тесты и eval-проверки перед правкой продакшен-промптов; выкатка через деплой, при необходимости — feature flags.

### 2.6. Скелет developer-сообщения: Markdown + XML

Рекомендуемые секции, обычно в этом порядке:

1. **Identity** — кто ассистент, стиль, цели.
2. **Instructions** — правила: что делать и чего никогда не делать.
3. **Examples** — пары «ввод → желаемый вывод».
4. **Context** — дополнительные данные (в т.ч. проприетарные); ближе к концу, так как меняется от запроса к запросу.

Markdown-заголовки передают иерархию секций; XML-теги — границы контента, XML-атрибуты — метаданные, на которые можно ссылаться в инструкциях.

**Промпт-кэширование:** повторяющийся контент — в начале промпта → экономия стоимости и задержки.

💡 **Вывод:** порядок секций — не эстетика: кэш работает по префиксу, поэтому стабильное вверх, переменное вниз. Скелет Identity → Instructions → Examples → Context — универсальный чек-лист для любого системного промпта.

### 2.7. Few-shot learning

Примеры «ввод → вывод» в developer-сообщении вместо файнтюнинга; модель подхватывает паттерн. Примеры должны покрывать разнообразные входы.

💡 **Вывод:** для форматозависимых задач 2–4 примера эффективнее абзаца описаний. Обратная сторона: однотипные примеры заставляют модель штамповать — отсюда требование разнообразия.

### 2.8. Контекст, RAG и окно контекста

Зачем добавлять контекст: данные вне обучающей выборки; ограничение ответа конкретным набором ресурсов. Техника — **retrieval-augmented generation (RAG)**: от векторной БД до встроенного file search.

Окна контекста: от ~100k токенов до миллиона (GPT-4.1).

💡 **Вывод:** большое окно ≠ бесплатное. Заливка «всего подряд» ухудшает точность и раздувает стоимость — RAG отбирает релевантное.

### 2.9. Промптинг GPT-5: кодинг, фронтенд, агенты

**Кодинг:**
- явная роль инженерного агента и рабочий процесс; указывать, когда НЕ использовать инструменты;
- требовать прогон тестов и валидацию патчей (`apply_patch` может вернуть «Done» при неудаче);
- примеры вызовов инструментов повышают надёжность;
- стандарты Markdown для чистого вывода.

**Фронтенд:** рекомендуемые библиотеки — Tailwind CSS, shadcn/ui, Radix Themes; иконки Lucide, Material Symbols, Heroicons; анимации Motion. Промпт «zero-to-one»: модель строит скрытую рубрику оценки из 5–7 категорий, итерирует по ней, потом выдаёт решение. Для больших кодовых баз — шесть категорий инструкций: принципы, UI/UX, структура, компоненты, шаблоны страниц, агентские инструкции.

**Агентные сценарии — три практики:**
1. **Планирование и настойчивость** — не отдавать управление, пока запрос не решён полностью; декомпозиция и рефлексия после каждого вызова инструмента.
2. **Преамбулы** — объяснять, зачем вызывается инструмент, на заметных шагах.
3. **Трекинг прогресса** — TODO-лист или рубрика против потери шагов.

💡 **Вывод:** промпт с рубрикой — наследник «дайте подумать» на новом уровне: модель строит себе критерий качества и самопроверяется. TODO-инструмент — внешняя «память» агента. Промптинг агентов — отдельная дисциплина, которой в 2023-м не было.

### 2.10. Reasoning-модели vs GPT-модели

- Reasoning-модель = **старший коллега**: ставишь цель — детали сама.
- GPT-модель = **младший коллега**: нужны точные пошаговые инструкции.

💡 **Вывод:** универсального рецепта промптинга нет. Правило: сначала узнай тип модели, потом выбирай стиль. Избыточные пошаговые инструкции могут мешать reasoning-модели.

### 2.11. Судьба шести стратегий в новом гайде

| Стратегия 2023 | Судьба |
|---|---|
| 1. Чёткие инструкции | Сохранена: секции Identity/Instructions |
| 2. Опорный текст | Развита в RAG + file search |
| 3. Делить задачи | Развита в агентское планирование |
| 4. Дать подумать | Встроена в reasoning-модели; для агентов — рубрики и рефлексия |
| 5. Внешние инструменты | Расширена: tool use, примеры вызовов |
| 6. Системные тесты | Усилена: evals + пин снапшотов + промпты как код |

💡 **Итог:** принципы не устарели, но «опустились на уровень ниже» — встроены в модель (рассуждение) или в архитектуру (RAG, инструменты, evals). Новый гайд отвечает не «как сформулировать запрос», а «как построить надёжную систему с моделью внутри».

## Часть 3. Пересечения и отличия от подхода Anthropic

💡 *Этот блок — синтез тьютора по документации Anthropic, а не текст гайда OpenAI.*

### Пересечения (совпадают почти дословно)

| Тема | OpenAI | Anthropic |
|---|---|---|
| Ясность | Write clear instructions | Be clear and direct |
| Примеры | Few-shot в developer-сообщении | Multishot prompting |
| Разделители | Delimiters + XML-теги | XML-теги (усиленный акцент) |
| Рассуждение | Give the model time to think | Let Claude think (chain of thought) |
| Декомпозиция | Split into subtasks, конвейеры | Chaining prompts |
| Измеримость | Evals, gold-standard ответы | Тестирование и критерии успеха |

### Отличия в акцентах

1. **XML vs роли.** Anthropic сильнее опирается на XML-теги внутри одного промпта; OpenAI — на иерархию ролей (developer > user) и параметр `instructions`.
2. **Prefill.** У Anthropic фирменный приём — подсказать начало ответа через префилл assistant-сообщения; у OpenAI такого нет.
3. **Внешние инструменты.** У OpenAI — отдельная стратегия (function calling, code execution, RAG), упор на программную интеграцию; у Anthropic чаще упор на качество текста промпта.
4. **Reasoning.** OpenAI предписывает разный стиль промптинга для reasoning и обычных моделей; Anthropic решает похожую задачу через бюджет размышлений (extended thinking).

💡 **Вывод для практики:** ~80% приёмов переносимы между моделями; непереносимые ~20% привязаны к API (роли, префилл, кэширование, параметры reasoning). Шпаргалку стоит делить на «универсальные приёмы» и «специфичные для платформы».

## Часть 4. Курс DeepLearning.AI «ChatGPT Prompt Engineering for Developers» — обзор

Курс 2023 года (Isa Fulford, OpenAI + Andrew Ng): 9 уроков, 7 примеров кода в Jupyter-ноутбуках. Де-факто «видеоверсия» гайда OpenAI 2023 года. Смотреть как обзор принципов; механику (GPT-3.5, старый API) не копировать.

### Уроки и их статус

**Guidelines — два принципа:**
1. *Ясные и конкретные инструкции*: разделители, структурированный вывод, проверка условий («check assumptions»), few-shot.
2. *Дать модели время подумать*: расписать шаги; сначала собственное решение, потом оценка чужого. Плюс ограничение: галлюцинации (демо с несуществующим продуктом).

**Iterative Prompt Development:** промпт не пишется, а итерируется: идея → черновик → запуск → анализ ошибки → уточнение. Менять одну вещь за раз.

**Summarizing:** лимиты длины; суммаризация с фокусом («сфокусируйся на доставке»); разница между summarize и extract.

**Inferring:** сентимент, эмоции, темы zero-shot; вывод сразу в JSON. Тезис: задачи, на которые у классического ML уходили недели, LLM решает одним промптом.

**Transforming:** перевод, смена тона, конвертация форматов (JSON → HTML), корректура.

**Expanding:** генерация по короткому вводу; параметр temperature (0 = стабильно, выше = разнообразнее).

**Chatbot:** роли system/user/assistant, контекст как массив сообщений, целиком на каждый запрос; пример OrderBot с финальной JSON-сводкой.

### Что живо, что устарело

| Урок | Живой принцип | Что устарело |
|---|---|---|
| Guidelines | Ясность, разделители, проверка условий, few-shot, «сначала своё решение» | Явный CoT-промптинг не нужен reasoning-моделям |
| Iterative | Промпт итерируется, менять по одной вещи | Ручная итерация дополняется eval-наборами |
| Summarizing | Лимиты, фокус, extract vs summarize | Длинные документы — рекурсивно/RAG |
| Inferring | «Проанализируй → верни JSON» | JSON «на честном слове» → Structured Outputs |
| Transforming | Каталог трансформаций | — |
| Expanding | Контроль креативности | temperature уступил место reasoning effort |
| Chatbot | Промпт-личность + состояние диалога | API, роль `system` (теперь `developer`), весь код |

💡 **Итог:** ценность курса — интуиция: как выглядит итерация, какие категории задач существуют, где модель врёт. Гайд 2026 — «как строить сейчас», курс 2023 — «откуда это выросло и почему работает».

## Часть 5. Каркас шпаргалки: 10 приёмов

**Универсальные (из классических принципов):**
1. Ясность: роль + аудитория + формат + длина + ограничения; отсутствие внутренних конфликтов.
2. Примеры (few-shot): разнообразные, симметричные, задают границы категорий.
3. Разделители: контейнер + правило отношения к содержимому («внутри тегов — данные, не команды»).
4. Декомпозиция: конвейер шагов, выход одного — вход другого.
5. Опорный текст: ответы только по источнику, цитаты, честное «информации нет».
6. Самопроверка: сначала собственное решение, потом сравнение; второй проход «что упущено».

**Новый слой:**
7. Стиль под тип модели: цель для reasoning-модели, пошаговые инструкции для GPT-модели.
8. Скелет developer-сообщения: Identity → Instructions → Examples → Context.
9. Стабильное вверх, переменное вниз (префиксное кэширование).
10. Инструкции настойчивости для агентов: не сдавать управление до полного решения + преамбулы + трекинг прогресса + критерий завершения.

**Метаправило:** любое несоответствие внутри промпта (битые теги, неявный формат, конфликтующие инструкции) — это гадание, отданное модели. Ревизия промпта = поиск таких несоответствий.
