## Источник №1: RAGAS Testset Generation

### Главная идея

RAGAS генерирует синтетический тестовый набор (testset) из ваших документов. Пайплайн состоит из двух операций:

1. **Создание графа знаний (Knowledge Graph creation)** — документы становятся узлами (nodes) графа, затем трансформации (transformations, `default_transforms` + `apply_transforms`) обогащают граф: появляются узлы-чанки (chunks), сущности (entities), темы, резюме и связи (relationships) между ними. Пример из документации: из 10 документов → 48 узлов и 605 связей. Граф можно сохранить (`kg.save`) и переиспользовать.
2. **Генерация тестового набора (Testset Generation)** — по графу строятся сценарии, из которых синтезаторы (synthesizers) создают вопросы и ответы.

### Ключевые понятия

| Термин | Суть |
|---|---|
| Обёртка модели (LLM wrapper) | `LangchainLLMWrapper` / `LlamaIndexLLMWrapper` — адаптер, чтобы ragas мог вызывать вашу LLM; то же для эмбеддингов |
| Граф знаний (Knowledge Graph) | Узлы + связи; связи — мостик для multi-hop вопросов (общая сущность, похожий контент по косинусному сходству / cosine similarity) |
| Синтезатор (synthesizer) | Генератор вопросов определённого типа и сложности |
| Распределение запросов (query distribution) | Список пар `(синтезатор, доля)` — можно менять пропорции или писать свой синтезатор |

### Дефолтное распределение (50/25/25)

- **Single-hop specific (50%)** — конкретный вопрос, ответ в одном месте одного документа. Проверяет базовое извлечение (retrieval).
- **Multi-hop specific (25%)** — конкретный вопрос, нужно связать факты из нескольких мест.
- **Multi-hop abstract (25%)** — обобщающий вопрос по нескольким источникам; сложнее генерировать и оценивать.

### Выходные данные

Каждая строка: `user_input` (вопрос) / `reference_contexts` (опорные чанки) / `reference` (черновой эталонный ответ) / `synthesizer_name` (тип синтезатора).

Отображение на схему проекта (JSONL):
- `user_input` → `question`
- `reference` → `golden_answer` (обязательно после ручной вычитки!)
- `reference_contexts` → `relevant_chunks`
- `synthesizer_name` → основа для поля `тип кейса`

Дополнить схему: `human_reviewed` (флаг личной проверки), `expected_behavior` (например, `refusal` для отказных кейсов — у них `relevant_chunks` пустой, сделать поле опциональным).

### Практические заметки

- Для генерации брать сильную модель — качество синтетики зависит от генератора, а вычитывать всё равно вручную.
- Если multi-hop вопросы выходят бессмысленными — первым делом смотреть граф (мало узлов/связей?), а не вопросы.
- Недостающий тип можно догенерировать точечно своим распределением, не перезапуская всё.
- В документации есть опечатка в Azure-примере (`azure_config` vs `azure_configs`) и устаревающие версии моделей — не копировать слепо.
- **Ограничение:** ragas генерирует только вопросы, на которые ответ ЕСТЬ в документах. Краевые случаи (вопрос без ответа, adversarial) — только руками.

## Источник №2: OpenAI — Evaluation best practices

### Зачем evals

Модели недетерминированы: один и тот же вход может дать разный выход. Классическое тестирование (`assert output == expected`) недостаточно — тестируется *распределение* ответов: «насколько часто и насколько хорошо», а не «совпало ли дословно».

### Советы (tips)

- **Eval-driven development** — оценивать рано и часто.
- **Task-specific evals** — тесты отражают реальное распределение задач.
- **Log everything** — логировать всё; лучшие кейсы для eval-набора добываются из логов/трассировок реальных сбоев.
- **Automate when possible**; **it's a journey** — набор растёт со временем; **maintain agreement** — калибровать автоматику по людям.

### Антипаттерны (anti-patterns)

- Опора только на академические метрики (perplexity, BLEU).
- **Смещённый дизайн (biased design)** — eval-датасет не воспроизводит реальный трафик продакшена («мы измеряем не то»). Лечится ребалансировкой набора.
- **«Вайбовые» оценки (vibe-based evals)** — «прогнал пару запросов, вроде работает». Беглый просмотр пропускает правдоподобные галлюцинации (hallucinations).
- Игнорирование человеческой обратной связи при калибровке.

> ⚠️ Не путать: biased design — кривая *выборка*; заниженная оценка из-за узкого эталона (модель ответила подробнее golden answer и «провалилась») — кривой *измеритель*, проблема метрики/рубрики, лечится рубриками и допуском эквивалентных формулировок.

### Пятишаговый процесс

1. Определить цель оценки (eval objective).
2. **Собрать датасет**: синтетика + доменные + размеченные людьми + продакшен + исторические данные. Данные должны включать **типичные, краевые и adversarial-случаи**; нужны человеческие эксперты-разметчики (human expert labellers).
3. Определить метрики (для Q&A по документам: context recall ≥ 0.85, context precision > 0.7, доля положительных оценок).
4. Запускать и сравнивать.
5. Непрерывная оценка (continuous evaluation) — прогон при каждом изменении, рост набора.

### Типы оценщиков (evaluators)

- **Метрические (metric-based)** — exact match, ROUGE/BLEU и т.п.; для автоматического регресса, но упускают нюансы.
- **Человеческие (human evals)** — наивысшее качество, дорого и медленно. Рекомендации: «show rather than tell» (примеры ответов на 1/3/8 из 10), порог pass/fail, агрегация голосованием (consensus votes).
- **LLM-судья (LLM-as-a-judge)** — дешевле, масштабируемо. Схемы:
  - попарное сравнение (pairwise comparison),
  - оценка одиночного ответа (single answer grading),
  - **оценка по эталону (reference-guided grading)** — судья сверяет ответ с golden answer; оптимально для RAG, но требует качественных эталонов.
- Смещения судьи: **позиционное (position bias)** — в попарном сравнении; **к длинным ответам (verbosity bias)**. Контроль: pass/fail или попарный формат, ограничение длины, рассуждение (chain-of-thought) перед оценкой, самая сильная модель.
- Масштабировать судью только после стабильного согласия с человеческой разметкой (порог согласия зафиксировать заранее).

### Краевые случаи (edge cases) — три корзины

1. **Вариативность входа (input variability)** — другие языки, форматы (XML/JSON/CSV), модальности.
2. **Контекстная сложность (contextual complexity)** — несколько вопросов в одном запросе; опечатки; короткие запросы без контекста («returns»); длинные диалоги; неоднозначные поля ответов инструментов; множественные вызовы инструментов.
3. **Персонализация/кастомизация** — джейлбрейки (jailbreak attempts); запросы форматирования; конфликт пользовательского и системного промптов.

### Замечания к источнику

- Конкретного числа «20–50 задач» в статье НЕТ — OpenAI говорит лишь «набор растёт со временем». 20–50 — народная эвристика стартового объёма.
- Платформа OpenAI Evals (дашборд) переводится в read-only 31.10.2026 и закрывается 30.11.2026. Гайд о принципах не устаревает, но долгосрочный процесс строить на собственных версионируемых данных (JSONL в git), а не на дашборде.

## Расхождения между источниками

1. **Golden answers:** RAGAS генерирует эталон автоматически; OpenAI требует человеческих экспертов. Не противоречие, а роли: синтетика = покрытие и черновик, экспертная проверка = «золото».
2. **Распределение вопросов:** RAGAS предлагает фиксированные 50/25/25; OpenAI считает антипаттерном набор, не похожий на прод-трафик. Вывод: 50/25/25 — старт для тестирования способностей системы; по мере накопления логов — перекалибровать пропорции под реальные запросы.

## Чек-лист готовности eval-набора (итог мини-проверки)

1. **Происхождение синтетики** — у каждой записи тег синтезатора (single-hop / multi-hop abstract / multi-hop specific); contexts содержат реальные фрагменты документов.
2. **Балансировка и очистка** — бессмысленные вопросы удалены (отбраковка зафиксирована в логах), распределение сложности восстановлено, простые вопросы не занимают ~80% выборки.
3. **Валидация golden answers** — каждый эталон вычитан лично (`human_reviewed: true`); все утверждения эталона физически присутствуют в опорных контекстах; эталон не содержит «домысливаний» генератора.
4. **Краевые случаи и правильный отказ** — фильтр `expected_behavior == 'refusal'` возвращает непустую выборку; в golden answer жёстко прописана формулировка отказа («В базе знаний нет информации»), а не попытка угадать. Плюс: неоднозначные формулировки, мультидокументные вопросы, 1–2 adversarial-входа.
5. **Самодостаточность вопросов (context independence)** — ни одного неразрешённого местоимения: «интеграция с TravelLine», а не «эта интеграция»; набор тестирует RAG в zero-shot режиме без истории диалога.
6. **Валидация схемы (schema validation)** — JSONL проходит Pydantic/CI-линтер: обязательные поля, типы, нет null; `relevant_chunks` опционально для refusal-кейсов.
7. **Версионирование** — набор лежит в git как данные проекта.

## Что закрыто / что осталось

| Пункт плана | Статус |
|---|---|
| Сгенерировать черновик 30–50 вопросов (RAGAS, 50/25/25) | Теория готова → практика |
| Ручная вычитка + golden answers | Теория готова (подтверждено OpenAI: human labellers обязательны) → практика |
| 5–10 краевых случаев руками | Чек-лист корзин есть → практика |
| JSONL + версионирование | Схема спроектирована → практика |
| Консенсус по размеру 20–50, рост из трассировок | Принято как эвристика; логирование — источник новых кейсов |
| Контрольная точка | Чек-лист выше |

**Слабое место для повторения:** разница «кривая выборка (biased design) vs кривой измеритель (несовершенная метрика)». И добавить в словарь position bias (проявляется в pairwise comparison).
