# День 36 — Зачем нужны evals: от vibe check к измерению

> Конспект по трём источникам: Hamel Husain «Your AI Product Needs Evals» (2024), OpenAI «Evaluation best practices», Anthropic «Demystifying evals for AI agents».

---

## 1. Главный тезис дня

**Корневая причина неуспешных LLM-продуктов — отсутствие системы оценки (evaluation system).**

- Vibe check («посмотрел глазами — вроде работает») полезен, но не отвечает на вопрос **«стало лучше или хуже?»**.
- LLM недетерминирована (nondeterminism): один и тот же промпт выдаёт разный текст при каждом запуске → проверяем **свойства выхода на наборе входов**, а не точное совпадение на 2–3 примерах.
- Без evals отладка реактивна: ждём жалоб → воспроизводим вручную → чиним → надеемся, что ничего не сломали («whack-a-mole» — чинишь один сбой, вылезает другой).
- Продуктовые evals (product evals, под задачи ваших пользователей) ≠ общие бенчмарки моделей (benchmarks, MMLU и т.п.).

**Скорость итераций = успех.** Нужны три процесса: оценка качества, отладка (debugging), изменение системы. Большинство занимается только третьим — и застревает на демо.

## 2. Источник №1 — Husain: три уровня оценки

Стоимость: Level 3 > Level 2 > Level 1 → отсюда частота запуска.

| Уровень | Что это | Когда гонять |
|---|---|---|
| **Level 1: Unit tests** | Утверждения (assertions), как в pytest: быстро и дёшево. Структура: фича → сценарии (feature → scenarios) + общие тесты (напр., regex «в ответ не утёк UUID») | При каждом изменении кода (CI) |
| **Level 2: Human & Model eval** | Логирование трасс (traces) → просмотр данных глазами → автоматическая оценка моделью (LLM-as-judge), выровненной с человеком | По расписанию |
| **Level 3: A/B testing** | Влияние на поведение реальных пользователей | Только для зрелых продуктов, после значительных изменений |

Ключевые практики:

- **Тест-кейсы генерируются синтетически** самой LLM — ждать продакшн-данных не нужно. Тесты пополняются по мере обнаружения новых сбоев.
- **100% проход не обязателен** — допустимый pass rate это продуктовое решение.
- **«Убери ВСЁ трение из просмотра данных»** (remove all friction from looking at data): свой инструмент просмотра/разметки за день на Gradio/Streamlit/Shiny. Начинать с бинарной разметки (good/bad).
- **«You can never stop looking at data»** — в начале читать все трассы, позже переходить к выборке.
- **LLM-судью калибруем по человеку**: таблица «ответ → критика модели → вердикт модели» против тех же колонок, заполненных экспертом (25–50 примеров за раз); итерируем промпт судьи; отслеживаем согласие (agreement) постоянно.
  - ⚠️ Сырое согласие (raw agreement) обманчиво при несбалансированных классах → считать **precision и recall** отдельно.
- **Бонусы бесплатно**: eval-система = движок данных для файнтюнинга (fine-tuning) + инфраструктура отладки. Файнтюнинг учит синтаксис/стиль/правила; RAG даёт контекст и актуальные факты.
- Принципы: начинать просто, не покупать модные инструменты; не доверять универсальным eval-фреймворкам — строить под свою задачу; использовать LLM для генерации тестов, синтетики, критики.

## 3. Источник №2 — OpenAI: процесс и анти-паттерны

### Анти-паттерны (anti-patterns)

1. **Vibe-based evals** — «кажется, работает» как стратегия.
2. **«Напишем evals перед релизом»** — откладывание оценки до конца.
3. **Слишком общие метрики** — полагаться только на академические (perplexity, BLEU).
4. **Смещённый дизайн (biased design)** — датасеты, не воспроизводящие реальный трафик.
5. **Игнорирование человеческого фидбека** — автоматика без калибровки по людям.

### Альтернатива: eval-driven development

Оценивать **рано и часто**; тесты под задачу на реальном распределении данных; **логировать всё** (логи — источник будущих eval-кейсов); автоматизировать; это путь, а не пункт назначения.

### 5-шаговый процесс

1. **Цель (eval objective)** — критерий успеха.
2. **Датасет** — источники: логи/продакшн-данные, экспертная разметка, синтетика (+ исторические, купленные). Включать типичные, краевые и состязательные (adversarial) случаи.
3. **Метрики** — с **пороговыми значениями** (напр., context recall ≥ 0.85), а не «хорошо/плохо».
4. **Прогон и сравнение** — итерации.
5. **Непрерывная оценка (continuous evaluation, CE)** — прогон при каждом изменении, мониторинг, пополнение набора.

### Где нужны evals: 4 архитектуры (по нарастанию недетерминизма)

- **Single-turn** → следование инструкциям (instruction following), функциональная корректность (functional correctness).
- **Workflow** (цепочка вызовов) → то же, но каждый шаг оценивается изолированно; новых источников недетерминизма нет.
- **Single-agent** → + выбор инструмента (tool selection) и точность аргументов (data precision).
- **Multi-agent** → + точность передачи управления (agent handoff accuracy). Решение о мультиагентности должны диктовать evals.

### Три типа оценщиков (evaluators)

- **Метрические**: exact match, ROUGE/BLEU, точность вызова функций, исполняемые проверки (executable evals). Дёшево, автоматизируемо, но без нюанса.
- **Человеческие**: золотой стандарт, но дорого и медленно. Примеры ответов на каждый балл, порог pass/fail, консенсус-голосование.
- **LLM-as-a-judge**: попарное сравнение / оценка одиночного ответа / оценка относительно эталона. Ловушки: позиционное смещение (position bias), смещение к длине (verbosity bias). Рецепт: попарное сравнение или pass/fail; самая способная модель-судья; рассуждение (chain-of-thought) перед вердиктом; контроль длины; масштабировать только после стабильного согласия с человеком.
- LLM лучше различают варианты, чем генерируют → оценки строить как сравнение/классификацию/скоринг по критериям.

## 4. Источник №3 — Anthropic: evals для агентов

### Словарь

- **Задача (task / test case)** — один тест: входы + критерии успеха.
- **Попытка (trial)** — одно выполнение задачи; задачу гоняют в нескольких попытках.
- **Грейдер (grader)** — логика оценки аспекта работы; внутри — утверждения (assertions / checks).
- **Транскрипт (transcript / trace / trajectory)** — полная запись попытки: вызовы инструментов, рассуждения, промежуточные результаты.
- **Исход (outcome)** — **финальное состояние среды**. «Ваш рейс забронирован» в тексте ≠ запись в базе. **Не верь самоотчёту агента — проверяй состояние среды.**
- **Оценочный стенд (evaluation harness)** vs **агентный стенд (agent harness / scaffold)**: оценивая «агента», оцениваешь модель + стенд вместе.
- **Набор оценок (evaluation suite)** — коллекция задач под конкретные способности.

### Outcome vs trajectory

- Исход = **что** достигнуто (state check среды). Траектория = **как** (число шагов, инструменты, ограничения).
- **«Грейди то, что агент произвёл, а не путь, которым шёл»** — проверка точной последовательности шагов хрупка и наказывает валидные неожиданные решения. Проверять свойства (какие инструменты, с какими аргументами) — можно; требовать точный порядок — нет.

### pass@k и pass^k

- **pass@k** — вероятность хотя бы одного успеха из k попыток: `1 − (1−p)^k`. Растёт с k. Для случаев «достаточно одного успеха» (кодинг: pass@1).
- **pass^k** — вероятность успеха во всех k попытках: `p^k`. Падает с k. Для клиентских агентов, где нужна надёжность **каждый раз** (пример: p=0.75 → pass^3 ≈ 42%).
- Демо живёт в логике pass@k, пользователь — в логике pass^k.

### Capability vs regression evals

- **Capability (quality)** — «что агент умеет?»: стартуют с низкого прохода, это «холм для взбирания».
- **Regression** — «всё ещё умеет?»: целевой проход ~100%, падение = поломка.
- **«Выпускной» (graduation)**: capability-набор с высоким проходом → регрессионный набор.

### Roadmap «с нуля до единицы» (Steps 0–8)

0. **Начни рано.** **Evals тем труднее строить, чем дольше ждёшь**: раньше требования сами становятся тестами, позже — реверс-инжиниринг критериев из живой системы. Хватит 20–50 задач из реальных сбоев.
1. Начни с того, что уже проверяешь вручную; источники — баг-трекер, очередь поддержки.
2. **Однозначные задачи + эталонное решение (reference solution)**: два эксперта должны независимо вынести одинаковый вердикт. **0% pass@100 — обычно сломанная задача, а не слабый агент.**
3. **Баланс классов**: тестировать и «должно произойти», и «не должно» — иначе односторонняя оптимизация.
4. **Стабильная среда, изоляция попыток** (пример: Claude читал git-историю прошлых попыток → нечестное преимущество).
5. **Грейдеры осмысленно**: детерминированные где можно, LLM где нужно, люди для валидации; частичный балл (partial credit); судье давать выход («Unknown»); каждое измерение — отдельным судьёй.
6. **Читай транскрипты** — иначе не отличить ошибку агента от ошибки грейдера. Провалы должны «выглядеть справедливо».
7. Следи за **насыщением (eval saturation)**: eval на 100% ловит регрессии, но не даёт сигнала роста. (Кейсы: Opus 4.5 на CORE-Bench 42% → 95% после починки грейдинга.)
8. **Eval suite — живой артефакт с владельцем**; задачи контрибьютят продуктовые команды и эксперты.

### Шесть методов оценки + «швейцарский сыр»

Автоматические evals, мониторинг продакшна, A/B-тесты, пользовательский фидбек, ручное чтение транскриптов, системные человеческие исследования. **Swiss Cheese Model**: ни один слой не ловит всё — комбинируем: автоматика для итераций + мониторинг для истины + люди для калибровки.

## 5. Типы грейдеров для агентов (Anthropic)

| Тип | Сильные стороны | Слабости |
|---|---|---|
| **Кодовые (code-based)**: строки, бинарные тесты, статанализ, проверка исхода и вызовов | быстро, дёшево, объективно, воспроизводимо | хрупкость к валидным вариациям, мало нюанса |
| **Модельные (model-based)**: рубрики, попарное сравнение, консенсус судей | гибко, масштабируемо, нюанс, открытые задачи | недетерминизм, цена, нужна калибровка по людям |
| **Человеческие**: экспертная проверка, spot-check, A/B | золотой стандарт | дорого, медленно |

Особенности по типам агентов: **coding** — детерминированные тесты (SWE-bench Verified, Terminal-Bench); **conversational** — вторая LLM симулирует пользователя, успех многомерен (τ-Bench, τ2-Bench); **research** — groundedness + coverage + качество источников, частая калибровка (BrowseComp); **computer use** — проверка исхода в реальной/песочной среде (WebArena, OSWorld).

## 6. Синтез трёх источников

- Все трое согласны: **vibe check — не стратегия**; смотреть на данные обязательно; LLM-судью калибровать по человеку; evals = топливо для файнтюнинга и улучшений.
- Husain режет мир **по стоимости/частоте** (3 уровня), OpenAI — **по архитектуре и типу оценщика**, Anthropic — **по анатомии агентного прогона** (task → trials → transcript/outcome → graders). Это ортогональные оси одной картины.
- Бинарная разметка (Husain) — старт; шкалы 1–5 с консенсусом (OpenAI) — когда есть ресурс на калибровку.
- «Не нужен 100% проход» (Husain) уточняется: для regression-набора 100% — норма (Anthropic).
- Проверка вызовов инструментов — про **свойства** (что вызвано, с какими аргументами), не про **порядок** шагов.

## 7. Контрольная точка: спич коллеге за 2 минуты

Тезис: **«И так видно, что работает» — не стратегия.**

Аргументы:
1. Модель недетерминирована → 2–3 просмотренных примера ничего не доказывают; проверяем свойства выхода на наборе входов (OpenAI).
2. Без evals правка промпта — игра whack-a-mole: чиним один сбой, молча ломаем другие; регрессию не отличить от шума (Husain).
3. Чем дольше ждём, тем труднее: позже придётся реверс-инжинирить критерии успеха из живой системы; 20–50 задач из реальных сбоев — достаточный старт (Anthropic).
4. Команды с evals обновляют модель за дни, без evals — за недели (Anthropic).

Что предлагаем вместо: (1) начать с ручных проверок и баг-трекера → 20–50 задач; (2) быстрые assertions при каждом изменении (Level 1 Husain); (3) логировать всё и читать трассы; (4) метрики с порогами + непрерывная оценка (5 шагов OpenAI); (5) pass^k для надёжности, а не разовые демо.
