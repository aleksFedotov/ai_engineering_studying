## 1. Базовая ментальная модель

**Инструмент (tool)** — контракт между детерминированной системой (deterministic system) и недетерминированным агентом (non-deterministic agent).

- Обычная функция: `getWeather("NYC")` всегда вызывается явно и возвращает одно и то же.
- Агент: даже на один и тот же вопрос может вызвать инструмент, ответить из общих знаний, уточнить детали или галлюцинировать параметр.

**Следствие:** инструменты проектируются не как API для программистов, а как интерфейс для агента. Описание инструмента (description) = документация, которая загружается в контекст модели при каждом ходе. Неоднозначность, которую человек «додумает», для модели — источник ошибок.

## 2. Методика Anthropic: прототип → оценка → итерация

### 2.1 Прототип (building a prototype)
- Собрать быстрый прототип и потестировать руками ДО отдачи модели.
- Обернуть в локальный MCP-сервер: `claude mcp add <name> <command> [args...]` (Claude Code) или Settings → Developer (Claude Desktop).
- Агенту-разработчику давать документацию (часто в виде `llms.txt`).

### 2.2 Оценка (evaluation)
- Задачи — реалистичные, на реальных данных, могут требовать десятков вызовов инструментов.
- **Сильная задача** проверяет способность найти стратегию: «Клиент 9182 сообщил о тройном списании. Найди записи в логах и определи, затронуты ли другие».
- **Слабая задача** диктует стратегию: «Найди в логах purchase_complete и customer_id=9182».
- Каждой задаче — проверяемый ответ (verifiable response): от точного сравнения до судьи-LLM. Не переспецифицировать ожидаемые вызовы (правильных путей несколько).
- Запуск: агентный цикл (agentic loop) — while-цикл, чередующий LLM и вызовы инструментов.
- Требовать блоки рассуждения/обратной связи ДО вызовов (цепочка рассуждений / chain-of-thought); у Claude — interleaved thinking.
- **Метрики:** точность (accuracy), время, число вызовов, потребление токенов, ошибки инструментов.
- Анализ: читать транскрипты (transcripts); то, что агент опускает, важнее сказанного. Пример Anthropic: модель добавляла «2025» в поисковый запрос — исправили описанием инструмента.
- Отложенный тестовый набор (held-out test set) против переобучения. Результаты Anthropic после оптимизации агентом: Slack 67,4 % → 80,1 %; Asana 79,6 % → 85,7 %.

### 2.3 Совместная работа с агентами
- Склеить транскрипты оценок → отдать Claude Code на анализ и рефакторинг инструментов.

## 3. Пять принципов эффективных инструментов (Anthropic)

### 3.1 Выбор правильных инструментов
- Больше инструментов ≠ лучше. Не оборачивать каждый API-эндпоинт.
- У агентов другие «возможности действий» (affordances): контекст ограничен, память компьютера — нет.
- `list_contacts` (вернуть всё) → брутфорс по токенам; лучше `search_contacts` / `message_contact`.
- **Консолидация (consolidation):**
  - `list_users` + `list_events` + `create_event` → `schedule_event`
  - `read_logs` → `search_logs` (только релевантное + контекст)
  - `get_customer_by_id` + `list_transactions` + `list_notes` → `get_customer_context`
- У каждого инструмента — ясная отдельная цель; пересекающиеся инструменты отвлекают.

### 3.2 Пространства имён (namespacing)
- Префиксы по сервису и ресурсу: `asana_search`, `jira_search`, `asana_projects_search`.
- Префикс vs суффикс влияет на качество — проверять на своей оценке.
- У OpenAI это конструкт схемы: `{"type": "namespace", "name": "crm", "tools": [...]}`.

### 3.3 Значимый контекст в ответах
- Возвращать высокосигнальные поля: `name`, `image_url`, `file_type` — да; `uuid`, `mime_type`, `256px_image_url` — нет.
- Агенты работают с именами на естественном языке лучше, чем с криптическими ID: замена UUID на осмысленные ref (или нумерацию с нуля) повышает точность и снижает галлюцинации.
- **Паттерн concise/detailed:** параметр `response_format` (enum): по умолчанию кратко (без ID), по запросу подробно (с ID для следующих вызовов). Экономия в примере Slack: 72 токена против 206.
- Формат ответа (XML/JSON/Markdown) влияет на качество — выбирать по своей оценке.

**Реализация замены UUID → ref (адаптерный слой):**
- Хранилище маппинга ref → UUID живёт в процессе сервера; UUID наружу не отдаётся.
- `register(uuid)` выдаёт стабильный `note_0`, `note_1`...; `resolve(ref)` — обратно, с ошибкой-навигатором («Неизвестный ref, доступные: ...»).
- Альтернатива: детерминированный slug из заголовка (если имена уникальны).

### 3.4 Токен-эффективность (token efficiency)
- Комбинировать пагинацию (pagination), диапазоны (range selection), фильтрацию (filtering), усечение (truncation) с разумными дефолтами.
- Claude Code: лимит ответа инструмента 25 000 токенов.
- При усечении — направлять агента текстом («сделайте несколько точечных запросов вместо одного широкого»).
- **Ошибки промпт-инжинирятся:** вместо кодов ошибок и трассировок — конкретные указания, как исправить вызов. Плохо: `Error: invalid param`. Хорошо: «Параметр date должен быть YYYY-MM-DD, получено 'завтра'. Пример: date='2026-09-27'».

### 3.5 Промпт-инжиниринг описаний (prompt-engineering tool descriptions)
- Описывать инструмент как новичку в команде: явно раскрывать неявный контекст (форматы, терминология, связи ресурсов).
- Однозначные имена параметров: не `user`, а `user_id`.
- Даже мелкие правки описаний дают большой эффект (пример: SWE-bench Verified).
- Для MCP — аннотации инструментов (tool annotations): деструктивность, доступ к открытому миру.

## 4. Best practices OpenAI (function calling guide)

### Терминология
- Инструмент (tool) → вызов инструмента (tool call) → результат вызова (tool call output, привязка по `call_id`).
- Цикл из 5 шагов: запрос с инструментами → tool call → выполнение в коде → запрос с результатом → финальный ответ.
- Функция = инструмент, описанный JSON Schema (`name`, `description`, `parameters`, `strict`).

### Пять блоков рекомендаций
1. **Ясные имена и описания.** Описывать назначение функции и каждого параметра (и формат), что означает вывод. **В системном промпте — когда и когда НЕ использовать каждую функцию.** Примеры и краевые случаи (edge cases) против повторяющихся сбоев (осторожно: примеры могут ухудшить reasoning-модели). Для отложенных инструментов: детали — в описание функции, описание namespace — кратким.
2. **Инженерные практики.** Принцип наименьшего удивления (principle of least surprise). Enum'ы против невалидных состояний: плохо `toggle_light(on, off)` — возможно `on=true, off=true`; хорошо `set_light(state: enum["on","off"])`. **Тест стажёра (intern test):** сможет ли человек использовать функцию, имея только то, что видит модель? Какие вопросы задаст? Ответы — в промпт.
3. **Снимать нагрузку с модели (гранулярность, правила 1–2):**
   - Не заставлять модель заполнять известные аргументы: если `order_id` уже есть в коде — `submit_refund()` без параметров.
   - Объединять функции, которые всегда вызываются подряд: `query_location()` + `mark_location()` → одна функция.
4. **Гранулярность, правило 3:** меньше ~20 функций на начало хода (мягкая рекомендация / soft suggestion). Для большого набора — поиск инструментов (tool search, `defer_loading`).
5. **Ресурсы:** Playground для схем; файнтюнинг при большом числе функций.

### Механизмы
- **Strict mode** (`strict: true`): аргументы гарантированно соответствуют схеме. Требования: `additionalProperties: false`, все поля в `required` (опциональные — `type: ["string", "null"]`). Устраняет структурные ошибки, но не семантические.
- **Tool search** (gpt-5.4+): отложенная загрузка редких инструментов; модель ищет инструмент → он подгружается → вызывается. Ответ на «много инструментов» решением модели; `allowed_tools` — ответ решением в коде.
- **Token usage:** определения функций идут в системное сообщение и тарифицируются как входные токены (input tokens).
- **tool_choice:** auto / required / конкретная функция / none / allowed_tools. **parallel_tool_calls:** несколько вызовов за ход.

## 5. Cookbooks: механика протокола (customer_service_agent.ipynb)

Протокол Anthropic API:
```
user вопрос → assistant [thinking + tool_use] → user [tool_result с tool_use_id] → assistant финальный ответ
```
- Сигнал вызова: `stop_reason == "tool_use"`; конец: `"end_turn"`.
- Результат инструмента возвращается в сообщении `role: "user"` блоком `tool_result` с `tool_use_id`. Сначала в историю добавляется ответ ассистента целиком, потом tool_result — порядок строгий.
- Схема инструмента называется `input_schema` (у OpenAI — `parameters`).

**Маппинг терминов Anthropic ↔ OpenAI:**
`tool_use` ↔ tool call · `tool_result` ↔ tool call output · `tool_use_id` ↔ call_id · `input_schema` ↔ parameters · аргументы: объект ↔ JSON-строка (`json.loads`).

**Критика примера по критериям дня:** инструменты кукбука — обёртки эндпоинтов (по ист. №1 лучше `get_customer_context`); модель заполняет `order_id`, который системе известен (нарушение правила ист. №2); описания минимальны. Вывод: механика протокола и дизайн инструментов — ортогональные навыки. Также в учебном цикле ноутбука история пересобирается на каждой итерации (теряются предыдущие вызовы) — в продакшене историю наращивать.

## 6. Расхождения источников (осознанно держать в голове)

| Тема | Anthropic | OpenAI | Синтез |
|---|---|---|---|
| Куда писать «когда / когда НЕ» | В описания инструментов | В системный промпт | Общая политика → системный промпт; специфика инструмента → description |
| Примеры в описаниях | Полезны (в т.ч. в ошибках) | Могут вредить reasoning-моделям | Зависит от модели — проверять оценкой |
| Namespacing | Соглашение об именах (префиксы) | Конструкт `namespace` в схеме | Одна идея, разная формализация |

Совпадения: тест стажёра ≈ «опиши новичку в команде»; объединение цепочек ≈ консолидация; меньше инструментов в контексте — выше точность.

## 7. Чек-лист хорошего инструмента (итог дня)

- [ ] **Тест стажёра пройден:** посторонний по одному определению выбирает правильный инструмент и правильно заполняет аргументы; вопросов стажёра — ноль (ответы внесены в description/системный промпт).
- [ ] Есть «когда вызывать» **и** «когда НЕ вызывать»; граница проведена в обе стороны между пересекающимися инструментами.
- [ ] Имена параметров однозначны (`item_id`, не `id`); форматы и примеры значений указаны.
- [ ] Гранулярность: известные коду значения не являются параметрами; функции, всегда вызываемые подряд, объединены; инструментов в контексте хода < ~20.
- [ ] Ответы высокосигнальные: без uuid/mime_type; ID — короткие осмысленные ref; есть concise/detailed при необходимости.
- [ ] Ошибки содержат указания, как исправить вызов; усечение — со стратегией для агента.
- [ ] Невалидные состояния невыразимы (enum, strict mode / валидация).
- [ ] Поведение при «не найдено», дубликатах, невалидном вводе — описано и соответствует коду.
- [ ] Есть оценка (evaluation) с реалистичными задачами и held-out test set; изменения проверяются метриками.

## 8. Мой пример: переписанные описания (после теста стажёра)

**Вопросы, которые задал «стажёр»:** формат ошибки при не-SELECT; формат результата; обрезка без LIMIT; полнота схемы БД и JOIN'ы; формат дат; стрелка «→» в FK; регистр exact match; дубликаты имён; «не найдено»; односторонняя граница между инструментами.

**Ключевые правки:** формат ошибки и результата явно; кап строк без LIMIT; `REFERENCES customers.customer_id` вместо «→»; поведение при дубликатах/отсутствии; симметричный WHEN NOT TO USE в обоих инструментах.

```python
{
    "type": "function",
    "name": "query_sql",
    "description": (
        "Executes a read-only SQL SELECT query against a local SQLite database with exactly two tables: "
        "customers(customer_id INTEGER PK, name TEXT, city TEXT, registered TEXT) and "
        "orders(order_id INTEGER PK, customer_id INTEGER REFERENCES customers.customer_id, "
        "product TEXT, amount REAL, status TEXT ['delivered','shipped','cancelled','processing'], created_at TEXT). "
        "Dates are ISO strings ('YYYY-MM-DD'). JOINs and subqueries are allowed; only SELECT is permitted — "
        "any data modification or DDL returns an error string 'ERROR: only SELECT queries are allowed'. "
        "Results are returned as a JSON array of row objects, capped at 50 rows even without LIMIT. "
        "IMPORTANT: orders with status 'cancelled' are refunded purchases — exclude them when computing spending. "
        "WHEN NOT TO USE: to look up one customer's profile by exact name, prefer get_customer_profile — "
        "it is simpler and less error-prone than writing SQL."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "query": {"type": "string",
                      "description": "The read-only SQL SELECT query to execute (e.g., 'SELECT * FROM customers WHERE customer_id = 1 LIMIT 5')."}
        },
        "required": ["query"],
        "additionalProperties": False,
    },
    "strict": True,
},
{
    "type": "function",
    "name": "get_customer_profile",
    "description": (
        "Looks up ONE customer by exact name (case-sensitive) and returns their profile "
        "(customer_id, name, city, registered) as a JSON object. "
        "If several customers share the name, returns all matches as a JSON array — inspect city/registered to disambiguate. "
        "If no match, returns the string 'customer not found' — check spelling or fall back to query_sql with LIKE. "
        "Typical use: finding a customer_id for subsequent order queries via query_sql. "
        "WHEN NOT TO USE: for order queries, aggregations, fuzzy search, or listing multiple customers — use query_sql instead."
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "name": {"type": "string",
                     "description": "The exact name of the customer (e.g., 'Мария' or 'Иван')."}
        },
        "required": ["name"],
        "additionalProperties": False,
    },
    "strict": True,
}
```
*(Допущения — формат ошибки, кап 50 строк, регистрозависимость, поведение при дубликатах, формат дат — сверить с реальным кодом.)*
