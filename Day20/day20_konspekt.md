## 1. Источник №1 — «Your Chunks Failed Your RAG in Production» (Towards Data Science)

### Главный тезис
Пайплайн RAG извлекает не документы, а **чанки** — форма фрагмента определяет всё downstream. Чанкинг стоит выше всех моделей стека: эмбеддинг-модель не исправит плохой чанк, re-ranker не поднимет неизвлечённый, LLM не ответит из контекста, который ей не дали. Ошибки чанкинга **молчаливые** (silent failure): система не падает, а уверенно отвечает «почти правильно».

### Три патологии формы чанка
| Форма | Проблема |
|---|---|
| Слишком большой | эмбеддинг усредняет несколько идей, ни одна не выигрывает retrieval (cosine similarity размыт) |
| Слишком маленький | точный, но оборванный; предложение без абзаца неинтерпретируемо |
| Режет логическую границу | информация целая в документе, но разрезана: каждый кусок в изоляции нерелевантен (кейс «подрядчик из Annex B») |

### Эволюция стратегий (хронология автора)
1. **Fixed-size** (512 ток / overlap 50): работает только для коротких однородных документов (FAQ, тикеты). Результат автора: context recall 0.72.
2. **Sentence windows** (`SentenceWindowNodeParser`): извлекать с точностью предложения, генерировать с контекстом окна (±3 предложения в метаданных, `MetadataReplacementPostProcessor` перед LLM). Recall 0.72 → 0.88 на повествовательных документах. Ломается на таблицах и коде. `window_size` подбирать под домен через RAGAS (автор тестировал 2/3/5).
3. **Иерархический чанкинг** (`HierarchicalNodeParser` [2048, 512, 128]): извлекать на уровне абзаца, генерировать на уровне раздела. `AutoMergingRetriever` поднимает листья к родителю при достаточном числе совпадений. Условие: ≥2 осмысленных уровня заголовков, иначе дегенерирует в fixed-size.
4. **Семантический чанкинг** (`SemanticSplitterNodeParser`): резать по сдвигу темы (семантическое расстояние соседних предложений > порога). Минусы: латентность индексации (эмбеддить каждое предложение, ~4x медленнее), чувствительность к `breakpoint_percentile_threshold` (95 → крупные чанки, 80 → осколки; автор остановился на 92). Лучше всего — на неструктурированных смешанных документах (Notion-экспорты).

### Таблицы — «чёрная дыра retrieval»
Таблица — 2D-структура, свёрнутая в 1D. После naive flattening связи «строка–колонка» исчезают: `«EMEA 4.2M 12% APAC 3.1M -3%»` неинтерпретируемо ни для эмбеддинга, ни для LLM.
**Лечение (источник №1):** каждая строка → естественно-языковое предложение («Product: Product A, Region: EMEA, Q3 Revenue: 4.2M…»). Торговля: теряется визуальная структура, чанки становятся семантически целыми. Для сложных таблиц (сводные, многоуровневые заголовки) — LLM-резюме на этапе индексации.

### PDF и слайды
- Стандартный PyPDF-loader перемешивает многоколоночные макеты. Лечение: PyMuPDF `get_text('blocks')` + сортировка блоков, pdfplumber для таблиц, Tesseract OCR для сканов (эвристика: < 50 слов/стр → скан).
- LlamaParse — managed-альтернатива, но: документы уходят наружу (data residency).
- Слайды: python-pptx (титулы, текст, заметки докладчика — информативнее тела). Для диаграмм — мультимодальная модель (GPT-4V / LLaVA). Эвристика: < 30 слов + есть картинка → мультимодальная обработка (~85% слайдов).

### Маршрутизация по типу документа (не «лучшая стратегия вообще»)
- spec/runbook/adr/contract → иерархический
- policy/hr/guide/faq → sentence windows
- pptx / сложный pdf → свой препроцессинг → TokenTextSplitter (256/30)
- дефолт → fixed-size (512/50)
- doc_type проставлять на этапе загрузки (ретроспективная разметка — боль).

### RAGAS как диагностика чанкинга
| Метрика | Ловит | Цель |
|---|---|---|
| Faithfulness | галлюцинации сверх контекста → чанки слишком большие | > 0.90 |
| Context Precision | шум в контексте → смешанные темы | > 0.75 |
| Context Recall | нужное не всплыло → разрыв границ | > 0.80 |
| Answer Relevancy | ответ мимо вопроса → окно узкое/широкое | > 0.85 |

**Ключевой паттерн:** recall ↓ при faithfulness ↑ → проблема в чанкинге/retrieval, НЕ в генерации. Принцип: «оценивай до оптимизации» — RAGAS до и после каждого изменения.

## 2. Источник №2 — Docling (официальный репозиторий + документация)

### Позиционирование
Open-source парсер (IBM Research → LF AI & Data, MIT). Закрывает тот слой, который в ист. №1 собирали руками (PyMuPDF + pdfplumber + python-pptx + Tesseract). Локальное исполнение — для чувствительных данных и air-gapped-сред.

### DoclingDocument — два класса полей
- **Content items**: `texts` (абзацы, заголовки, формулы), `tables` (TableItem + структурные аннотации), `pictures`, `key_value_items`.
- **Content structure**: `body` (дерево основного текста — **здесь порядок чтения**), `furniture` (колонтитулы — **не входят в body**), `groups` (контейнеры: списки, главы).
- Плюс у элементов: bounding box, provenance, label.
- Лечит: колонтитулы (furniture), перемешанные колонки (дерево body вместо порядка символов), таблица не превращается в кашу (TableItem).

### Экспорт
Markdown, HTML, JSON (lossless), DocTags. Важно: Markdown-экспорт **плоский** — теряет связи (caption ↔ таблица, иерархия), furniture исчезает совсем.

### Нативные чанкеры (путь №2, альтернатива «Markdown → свой сплиттер»)
- `BaseChunker`: `chunk()` + `contextualize()` (сериализация для эмбеддинга).
- **HierarchicalChunker**: чанк на элемент документа, сливает пункты списков, прикрепляет заголовки и подписи.
- **HybridChunker**: иерархический + два прохода (разрез по лимиту токенов токенизатора эмбеддинг-модели; merge мелких соседей с одинаковыми заголовками, `merge_peers=True`).
- **LineBasedTokenChunker**: целостность строк (таблицы, код, логи).
- **Ключевое:** `repeat_table_header=True` (по умолчанию) — при разрезании таблицы заголовок повторяется в каждом чанке-куске; `omit_header_on_overflow=False` — для широких строк.

### Оговорки
- Python ≥ 3.10 (с 2.70.0).
- Модели под капотом имеют собственные лицензии (MIT — только код).
- VLM-пайплайн (`--pipeline vlm`, например granite_docling) — другая точка компромисса скорость/качество, не путать с классическим чанкингом.

## 3. Источник №3 — «Unstructured vs LlamaParse vs Docling» (Kanopy Labs, 2026)

⚠️ Блог консалтинговой компании (конфликт интересов), методология не воспроизводима — цифры как порядок величин, не как истина.

| | Unstructured | LlamaParse | Docling |
|---|---|---|---|
| Профиль | 30+ форматов («швейцарский нож») | специализация PDF/DOCX/PPTX, под LLM | локальный OSS, сильный layout |
| Таблицы (бенчмарк) | 71% (hi_res); 42% (fast) | **89%** | 83% |
| Порядок чтения | 85% | 91% | **94%** |
| Скорость | fast ~0.5 с/стр.; hi_res 15–30 с/стр. | 3–8 с/стр., пики 45 с | ~0.8 с/стр. CPU |
| Развёртывание | OSS + облако | только облако | полностью локально |
| Цена на 100K стр./мес | $500–800 | ~$300 | $50–100 CPU / ~$400 GPU (5x быстрее) |

- **RAG recall@5:** Docling 78% > LlamaParse 76% > Unstructured (by-title) 72%. Вывод: *как чанкуешь важнее, чем как парсишь*; структурно-осознанный чанкинг даёт преимущество.
- Выбор: Unstructured — покрытие форматов; LlamaParse — PDF с таблицами (проверить compliance); Docling — регулируемые отрасли, структура, бюджет. Гибрид: Docling для PDF + Unstructured для остального.
- Дашборд качества парсинга: % страниц с нулевым текстом, средняя длина текста/стр., число таблиц found vs expected, золотой набор 50–100 документов.
- Препроцессинг: снять пароли (все три **молча проваливаются** на зашифрованных PDF!), TIFF→PDF, документы >100 стр. резать, «50 строк Python убирают 80% сбоев».
- У Docling дефолтный EasyOCR хуже Tesseract на английском — переключать бэкенд.

## 4. Расхождения между источниками

1. **Таблицы:** ист. №1 — verbalизация строк (жертвуем структурой ради читабельности); ист. №2/№3 — сохранение структуры + структурный чанкинг (repeat_table_header), recall@5 не хуже. Verbalизация предпочтительна для фактических запросов «значение из ячейки»; структура — для сопоставлений/вычислений по таблице целиком. Это две ступени, а не конкуренты.
2. **Self-host vs облако:** ист. №1 (старше) советовал LlamaParse командам без ресурсов; к 2026 зрелый локальный Docling ($50–100/мес CPU) снимает эту дилемму.
3. **«Поддерживает формат» ≠ «поддерживает хорошо»:** README Docling декларирует e-mail/XLSX; практика (ист. №3) для таких форматов рекомендует Unstructured.

## 5. Практика (мой пайплайн)

Скрипт: `practise.py` — Docling `convert_all` → экспорт `.md` → `RecursiveCharacterTextSplitter.from_tiktoken_encoder(cl100k_base)` → чанки в `chunks.jsonl` (id, source, chunk_index, text, tokens).

Тестовый корпус (3 PDF, сгенерированы для практики):
1. `report_finance_simple.pdf` — простая таблица (3 колонки).
2. `report_compliance_complex.pdf` — таблица с объединёнными ячейками (супер-заголовки, категория на 2 строки) + раздел «Исключения».
3. `guide_multicolumn.pdf` — двухколоночный макет + колонтитулы + узкая таблица.

### Что подтвердилось на практике
- Колонтитулы в чанки **не попали** (furniture отработал).
- Порядок чтения колонок корректный.
- Сложная таблица: Docling сплющил объединённые заголовки в составные имена колонок («Документы - Обязательные»), объединённую ячейку продублировал по строкам — корректный flattening, но семантика «одна сущность» потеряна.

### Список из 7 реальных дефектов (контрольная точка дня)
| # | Дефект | Где пойман | Лечение |
|---|---|---|---|
| 1 | Сиротский заголовок (чанк кончается на `## Шаг 2` без содержимого) | guide, chunk_0 и chunk_2 | иерархический чанкинг / фильтр обрывков |
| 2 | Дубли через overlap (~10% токенов повтор) | guide chunk_0→1 | контроль overlap, дедупликация |
| 3 | Потеря семантики объединённой ячейки («B - регулируемый» → две строки) | compliance (парсинг) | LLM-резюме / verbalизация |
| 4 | Разрыв логической границы — **предотвращён** (overlap 50: «Раздел 6. Исключения» целиком в одном чанке) | compliance chunk_4 | overlap / sentence windows |
| 5 | **Разрезанная таблица, нижний кусок без заголовков** (`| C - публичный | NDA | - | 3 | 1 |`, 24 токена, голая строка) | compliance chunk_2/3 при chunk_size≈150–200 | `repeat_table_header=True` (HybridChunker) |
| 6 | Подпись таблицы оторвана от таблицы («Таблица 2…» — отдельный чанк из 59 токенов) | compliance chunk_1, finance chunk_0 | нативные чанкеры Docling / приклеивание caption |
| 7 | Чанк из одних дубликатов (196 токенов = 2 одинаковых абзаца) | guide chunk_1 | дедупликация / merge с соседом |

### Чек-лист ручного аудита чанков (для повторного использования)
- □ В чанке нет колонтитулов (номера страниц, шапки «Имя компании»)?
- □ Чанк из середины таблицы содержит заголовки колонок?
- □ Текст многоколоночных страниц в правильном порядке?
- □ Нет пустых / однословных / дублирующихся чанков?
- □ Логические сущности (правило + исключение) не разрезаны границей?
- □ Заголовки не «сироты» (есть содержимое в том же чанке)?
- □ Подписи таблиц/рисунков прикреплены к объекту?

## 6. Формулы-шпаргалки

- **Диагноз по метрикам:** recall ↓ + faithfulness ↑ → чанкинг/retrieval; faithfulness ↓ → генерация/слишком большие чанки; precision ↓ → шумные/переразмеренные чанки.
- **Пайплайн «взрослый»:** парсер (Docling) → [опц.] verbalизация таблиц → чанкер структурный (HybridChunker) → эмбеддинг → RAGAS до/после.
- **Пайплайн «учебный/гибкий»:** Docling → Markdown → свой сплиттер → ручной аудит по чек-листу.
