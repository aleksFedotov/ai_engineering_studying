# День 27 — Отладка и оценка retrieval (конспект)

> Материал трёх источников дня + разъяснения тьютора. Термины: русский (английский оригинал).

---

## 1. Главная идея дня

Большинство проблем качества RAG — это проблемы **поиска (retrieval)**, а не генерации. Качество генерации не может превысить качество поиска: если нужный документ не дошёл до LLM, никакой промпт и никакая модель это не компенсируют.

Поэтому:
- поиск и генерацию оценивают **отдельно**, поиск — **первым**;
- отладку ведут по порядку шагов пайплайна, а не «чинят промпт»;
- цель — **число, а не ощущение**: «retrieval находит нужное в топ-5 в X% случаев».

---

## 2. Golden test set (золотой набор)

- 50–200 пар «запрос → id релевантных документов» (ground truth — эталонная разметка). Источники: реальные логи, саппорт-тикеты, вручную написанные кейсы.
- Реальные запросы лучше синтетических; синтетикой дополняют краевые случаи.
- **Важно про 30 кейсов (план):** допустимый старт, но 1 запрос = 3.3 п.п. метрики. Дельты в 1–2 запроса — шум, а не улучшение. Для уверенности: расширить набор, прогнать несколько раз / использовать точный поиск (exact search) из-за недетерминизма ANN, смотреть *какие* запросы поменяли статус.
- Каждый продакшн-сбой → новый тест-кейс (failure case mining). Версионировать набор вместе с корпусом.

## 3. Метрики

### 3.1. Сводная таблица

| Метрика | Вопрос | Когда главная |
|---|---|---|
| **Recall@k / Hit@k** | Есть ли релевантный документ в топ-k? | Главный «гейт» RAG — «нашли ли вообще?» |
| **MRR** | Как высоко первый релевантный? | Когда в LLM уходит топ-1/топ-3 |
| **nDCG@k** | Стоят ли релевантные выше нерелевантных (с градациями)? | Несколько релевантных документов, градуированная разметка |
| **Precision@k** | Какая доля топ-k релевантна? | После реранкера; контроль «раздутости» контекста |
| **F-beta** | Баланс точности и полноты | Медицина/юриспруденция (β>1), потребительский поиск (β<1) |

### 3.2. Формулы

```
Recall@k (hit-rate) = (число запросов, где релевантный документ попал в топ-k) / (всего запросов)

MRR = среднее по запросам (1 / ранг первого релевантного документа)   # запрос без попадания → 0

Precision = |Релевантные ∩ Найденные| / |Найденные|
Recall (per-document) = |Релевантные ∩ Найденные| / |Релевантные|

Fβ = (1 + β²) · (P · R) / (β² · P + R)      # β>1 → акцент на полноту, β<1 → на точность, β=1 → F1

DCG@k  = Σᵢ₌₁..k (2^relᵢ − 1) / log2(i + 1)     # экспоненциальный выигрыш, градации 0–3
NDCG@k = DCG@k / IDCG@k                          # IDCG — DCG идеального порядка; диапазон [0, 1]
```

**Два варианта DCG** (оба легитимны, не смешивать в одном эксперименте):
- линейный: `relᵢ / log2(rank + 1)` (код источника №1);
- экспоненциальный: `(2^relᵢ − 1) / log2(rank + 1)` (источник №2, классика Järvelin–Kekäläinen).

**Зачем нормализация в nDCG:** у разных запросов разный максимально возможный DCG; сырой DCG дал бы «богатым» запросам непропорциональный вес. Деление на IDCG приводит всё к шкале [0, 1].

**Два определения Recall (не путать!):**
- **per-query / hit-rate**: «нашёлся ли хотя бы один релевантный?» (источник №1, пороги плана, контрольная точка);
- **per-document**: «какую долю всех релевантных нашли?» (источник №2, нужен для F-beta).
Пример: отмечено 3 чанка, найден 1 → hit-rate = 1.0, per-document = 0.33.
Основная метрика для контрольной точки плана — hit-rate (пороги написаны под него); per-document и F₂ — дополнительной строкой для вопросов с несколькими чанками.

### 3.3. Пороги и ориентиры

**Recall@5:**
- < 0.60 — retrieval сломан, чинить до деплоя;
- 0.60–0.80 — приемлемо: оптимизировать чанкинг и поиск;
- 0.80–0.90 — хорошо: фокус на реранкинг и генерацию;
- > 0.90 — отлично, убывающая отдача.

**MRR:** > 0.70 — первый релевантный обычно в топ-2; > 0.85 — отлично.
**Высокий Recall@5 + низкий MRR** = документы находятся, но ранжируются низко → реранкинг (важнее, чем чанкинг).

**Пример ручного счёта nDCG@3**, градации [1, 3, 0]:
DCG@3 = 1/1 + 7/1.585 + 0/2 ≈ 5.42; IDCG@3 = 7/1 + 1/1.585 + 0 ≈ 7.63; NDCG@3 ≈ 0.71.

### 3.4. Пример F-beta

P = 0.8, R = 0.9, β = 2 → F₂ = 5·0.72 / 4.1 ≈ 0.878 (F1 при тех же P, R = 0.847 — β=2 «тянет» к полноте).

### 3.5. Правила работы с метриками

- **Менять одну переменную за раз** (чанк → замер → гибрид → замер → реранкер → замер), иначе улучшение не атрибутируется.
- k подбирать под то, что реально уходит в LLM; @10 — «запас» для оценки реранкера.
- Реранкер переставляет кандидатов внутри пула → Recall@k неподвижен, растут MRR / nDCG / Precision@3.
- Агрегаты говорят «сколько падает», разбор упавших запросов — «почему».
- CI-гейт: падение Recall@5 > 2% блокирует деплой.

## 4. Метрики генерации (RAGAS, обзорно)

RAGAS использует **LLM как судью** (читает вопрос, контекст, ответ):

| Метрика | Что измеряет |
|---|---|
| **Faithfulness (достоверность)** | Доля утверждений ответа, подтверждённых контекстом |
| **Answer Relevancy** | Отвечает ли ответ на вопрос (через сгенерированные вопросы по ответу) |
| **Context Utilization** | Какая доля ответа опирается на контекст |
| **Noise Sensitivity** | Деградация при добавлении нерелевантного текста |

⚠️ В источнике №2 формулы RAGAS упрощены (особенно Answer Relevancy и Noise Sensitivity) — при внедрении сверяться с документацией RAGAS. Для текущего плана RAGAS не нужен: сначала закрыть retrieval (Recall@5 > 0.80), потом генерацию.

## 5. Шесть режимов сбоя RAG (источник №3)

Конвейер: загрузка → чанкинг → индексация → поиск → ранжирование → сборка контекста → генерация. Симптом виден на выходе, корень — раньше.

### 5.1. Плохой чанкинг (bad chunking)
- **Симптомы:** ответ в документе есть, в контексте — нет; чанк с половиной ответа (правило без исключения); расплывчатые ответы; смена модели не помогает.
- **Лечение:** структурно-осведомлённый чанкинг (заголовки, подписи таблиц в чанке), резка по смысловым границам; overlap только где нужен; метаданные (документ, секция, версия, дата, доступ); тест: «может ли чанк сам ответить на реалистичный вопрос?»
- **Связь с планом:** эксперимент 256 vs 512 проверяет именно этот класс. Recall@5 ловит «найден ли чанк», но не «полуответ» — смотреть содержимое найденных чанков вручную.

### 5.2. Слабый поиск (weak retrieval)
- **Симптомы:** чанки «в правильном районе, не тот дом»; теряются точные термины (имена, ID, коды ошибок, даты); топ-1 слабее нижних (проблема ранжирования); многочастный вопрос покрыт частично.
- **Лечение:** гибрид (dense + keyword): векторы — за семантику/перефразировки, keyword — за точные идентификаторы; реранкер; переписывание и декомпозиция запросов; изолированный замер recall/precision.

### 5.3. Переполнение контекста (context overflow)
- **Симптомы:** ответ ухудшается при добавлении чанков; модель смешивает факты из разных источников; нужное утонуло в отвлекающем; рост latency/стоимости без прироста точности.
- **Лечение:** бюджет контекста по качеству доказательств (скоры, свежесть, авторитетность), а не по ёмкости окна; дедупликация/сжатие; стадийный поиск (кандидаты → реранк → компактный контекст); организованный промпт с метаданными.
- **Примечание:** k — ручка в обе стороны: больше k → выше recall, но риск overflow.

### 5.4. «Потерянная середина» (lost-in-the-middle)
- **Симптомы:** доказательство в промпте есть, в ответе — нет; перемещение фрагмента в начало/конец меняет ответ; длинные промпты снижают faithfulness.
- **Лечение:** порядок контекста по релевантности (сильнейшее — в начало); уменьшать середину (агрессивный реранк); несколько маленьких контекстов для сложных задач; тест позиционной чувствительности.

### 5.5. Устаревшие данные (stale data)
- **Симптомы:** ответ подтверждён источником, но конфликтует с текущей политикой; несколько почти одинаковых версий документа; «почти верно, но устарело». Семантическое сходство делает версии неразличимыми для ретривера.
- **Лечение:** метаданные свежести (даты, версия, статус); фильтры/буст по свежести и авторитетности; надёжная переиндексация (change detection, удаления); правила «источника истины»; показывать даты/версии модели.

### 5.6. Проигнорированный контекст (ignored context)
- **Симптомы:** ответ противоречит найденным доказательствам; общий ответ вместо конкретного из источника; неподдержанные детали; усиление инструкций меняет ответ при том же retrieval.
- **Лечение:** явная инструкция grounding («только из источников», «скажи, если данных недостаточно»); проверки атрибуции (какой пассаж подтверждает утверждение); отдельный валидационный проход; чёткий формат промпта (метки источников, даты, ответ перед пояснением).
- **Ловушка:** этот сбой заставляет бесконечно крутить retrieval, хотя retrieval исправен.

### 5.7. Соответствие классификации плана

| План (5 классов) | Источник №3 (6 режимов) |
|---|---|
| чанкинг | bad chunking |
| retrieval | weak retrieval |
| сборка контекста | context overflow + lost-in-the-middle |
| генерация | ignored context |
| устаревшие данные | stale data |
| — (нет в плане) | «нет ответа в данных» и «сбой загрузки/индексации» (шаги 1–2 чек-листа) |

## 6. Чек-лист отладки (по порядку, остановиться на первом сломанном шаге)

1. Ответ вообще **есть в исходных данных**?
2. Источник **загружен и проиндексирован** (джобы, парсинг, права, удаления)?
3. **Чанк** сохранил заголовок/определения/исключения/соседний контекст?
4. **Тест поиска без генерации**: ожидаемый чанк в топе? (→ Recall@k, MRR)
5. **Фильтры и метаданные** не отсекают нужное / не включают лишнее?
6. **Финальный промпт**: чанк не выброшен, не урезан, не в «середине»?
7. **Ответ vs доказательства**: неподдержан при хороших доказательствах → grounding, атрибуция, валидация.

Это готовая процедура для разбора вчерашних неудач по классификации сбоев.

## 7. Типичные ошибки при оценке (источник №1)

1. Оценивать только end-to-end ответы — смешиваются стадии.
2. Слишком маленький тест-набор (5 запросов — анекдот; минимум ~50).
3. Нерепрезентативный набор (только лёгкие запросы завышают метрики; нужны перефразировки, неоднозначные, мультидокументные).
4. Не обновлять набор при изменении корпуса.
5. Менять несколько переменных сразу.
6. Игнорировать разбор конкретных сбоев.
7. Не автоматизировать оценку в CI.

## 8. Карта «симптом → метрика/проверка → класс сбоя»

| Наблюдение | Метрика/проверка | Вероятный класс |
|---|---|---|
| Нужный чанк не в топ-k | Recall@k низкий | чанкинг / retrieval / нет данных / индексация |
| Чанк найден, но низко | MRR низкий при Recall ок | ранжирование → реранкер |
| Мусор в топ-k | Precision@k низкий | retrieval / сборка контекста |
| Ответ хуже при большем k | сравнение ответов при k=5/10/15 | context overflow |
| Ответ зависит от позиции чанка | позиционный тест | lost-in-the-middle |
| «Почти верно, но устарело» | проверка дат/версий источников | stale data |
| Ответ противоречит хорошему контексту | Faithfulness (RAGAS) / ручная сверка | ignored context |

## 10. Результаты практики

### Стенд

- Корпус: 61 англоязычная статья Wikipedia (PDF), кластеры: ML/нейросети, Древний Рим, космос, версии одной темы (полигон stale data), далёкие темы (дистракторы).
- Чанкинг: docling HybridChunker + contextualize(), слияние мелких чанков, фильтр «мусора» (формулы/артефакты таблиц), дедупликация (exact; near-dup ≥90% оставлены сознательно). Итог: 512 → 1503 чанка (медиана 271 слово), 256 → 3012 чанков (медиана 136).
- Модель: intfloat/e5-base-v2, префиксы «query: »/«passage: » обязательны (только для dense; в BM25-запрос префикс не добавлять!), normalize_embeddings=True.
- Индекс: Qdrant, отдельные коллекции на каждую руку эксперимента; гибрид — named vectors {dense, sparse(BM25, fastembed)} + Prefetch×2 + FusionQuery(RRF). ID поинтов — uuid5, строковый chunk_id — в payload (сравнение с golden set идёт по payload["chunk_id"]!).
- Реранкер: cross-encoder/ms-marco-MiniLM-L-6-v2, топ-20 → топ-5; в ~50 раз медленнее поиска (1 it/s против ~29 it/s).

| Конфигурация | R@1 | R@5 | MRR@5 |
|---|---|---|---|
| 512 dense | 73.4% | 100% | 0.8466 |
| **512 hybrid** | **85.9%** | **98.4%** | **0.9021** |
| 512 hybrid + rerank | 81.2% | 100% | 0.8919 |
| 256 dense | 71.4% | 100% | 0.8225 |
| 256 hybrid | 73.0% | 98.4% | 0.8360 |
| 256 hybrid + rerank | 79.4% | 98.4% | 0.8757 |

### Вердикт эксперимента

1. **Финальная конфигурация: 512 токенов + гибрид (dense + BM25), без реранкера.**
2. Гибрид vs dense на 512: +8 хитов на R@1 (55 vs 47) — не шум (1 запрос = 1.6 п.п.). Механизм объясним: BM25 вытаскивает точные совпадения (дата «221 BC» в q_063 — dense её размывал, гибрид нашёл).
3. Реранкер не окупается: хуже на R@1 и MRR@1, выигрыш на R@5 = 1 запрос (шум), цена — ×50 латентности. Не «реранкеры бесполезны», а «на этом корпусе/сете выигрыш не доказан».
4. 512 > 256: на мелких чанках dense проседает (теряется контекст); гибрид и реранк на 256 дают наибольший относительный прирост, но всё равно не догоняют 512.
