# День 29 — Как tool use работает под капотом

**Источники:**
1. OpenAI Function calling guide — https://developers.openai.com/api/docs/guides/function-calling
2. How does Function Calling work in LLMs (Outcome School) — https://outcomeschool.com/blog/how-does-function-calling-work-in-llms

---

## Ключевая идея

**Модель не исполняет функции.** Она только генерирует структурированный запрос на вызов — имя функции + аргументы в виде JSON-строки. Исполняет функцию код вашего приложения.

Поэтому фраза «модель вызвала функцию» технически неверна. Правильно: **модель сгенерировала запрос на вызов (tool call), приложение его исполнило**.

Метафора: модель — **мозг (brain)**, решает *что* делать; приложение — **руки (hands)**, реально выполняют действие.

---

## Зачем это нужно: два разрыва LLM

- **Разрыв живых данных (live data gap)** — модель обучена на текстах прошлого и не может ничего «посмотреть». Вопрос «какая погода в Париже сейчас?» без инструментов → уверенный, но выдуманный ответ = **галлюцинация (hallucination)**.
- **Разрыв действий (action gap)** — модель не может ничего *сделать*: ни отправить письмо, ни забронировать, ни оплатить. «У неё нет рук».

Function calling закрывает оба разрыва: модель решает, какой инструмент нужен; код (который и так умеет ходить в API) исполняет.

> Function calling снижает галлюцинации не потому, что модель «поумнела», а потому что ей подкладывают реальные данные вместо догадок.

---

## Пятишаговый цикл (tool calling flow)

1. **Запрос к модели**: промпт пользователя + схемы доступных инструментов.
2. **Модель возвращает tool call**: имя функции + аргументы (JSON-строкой).
3. **Код приложения исполняет функцию** с этими аргументами (`json.loads` → вызов).
4. **Результат отправляется обратно** в диалог как сообщение с ролью `tool`, с привязкой через `call_id`.
5. **Модель выдаёт финальный текстовый ответ** — или ещё один tool call (цикл повторяется).

Пример диалога («какая погода в Париже?»):

```
user : "What is the weather in Paris?"
model: tool call -> get_weather("{\"location\": \"Paris, France\"}")
tool : { "temperature": 18, "condition": "sunny" }
model: "The weather in Paris is 18 degrees and sunny."
```

Важно:
- аргументы в tool call — это **JSON-строка**, её нужно парсить (`json.loads`);
- `call_id` связывает результат с конкретным вызовом — без него при нескольких вызовах модель могла бы подставить результат «не туда» (погоду Парижа — к вызову отправки письма);
- история диалога сохраняется полностью — модель каждый раз видит всё: вопрос, свои tool calls, результаты.

## Схема инструмента: три элемента

| Поле | Назначение |
|---|---|
| `name` | имя функции, например `get_weather` |
| `description` | когда и как использовать функцию — на естественном языке; напрямую влияет на выбор инструмента моделью |
| `parameters` | JSON Schema входных аргументов |

**«Пустая форма» (blank form)**: `parameters` описывает только *форму* данных — какие поля есть, их типы, обязательность, допустимые значения (enum) — **без самих значений**. Значения модель вписывает позже, в tool call.

```json
{
  "name": "get_weather",
  "description": "Retrieves current weather for the given location.",
  "parameters": {
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "City and country" }
    },
    "required": ["location"]
  }
}
```

## Токены: схемы стоят денег при каждом запросе

Под капотом определения функций **подставляются в системное сообщение** в специальном синтаксисе. Следствия:

- схемы занимают контекстное окно и оплачиваются как **входные токены (input tokens)** при *каждом* запросе — даже если пользователь написал «привет»;
- пример: 50 инструментов × ~200 токенов = ~10 000 входных токенов в каждом запросе;
- много инструментов также **снижают точность выбора** (модели труднее выбрать из 60 похожих описаний).

Как снизить расход и повысить точность:
- держать мало инструментов (рекомендация OpenAI — **меньше ~20** на старте);
- короткие и точные описания;
- **tool search** — отложенная загрузка редко используемых инструментов;
- (продвинуто) fine-tuning.

## Multi-step vs parallel: критерий — зависимость данных

- **Параллельные вызовы (parallel)** — данные независимы: «сравни погоду в Париже и Лондоне» → два tool call в одном ответе, код исполняет оба, оба результата уходят обратно одним пакетом. Экономит запросы к API.
- **Многошаговые вызовы (multi-step)** — следующий вызов зависит от результата предыдущего: `get_user → get_order → refund`. Только последовательно, каждый шаг — виток цикла.

**Счёт запросов к API**: новый запрос к модели нужен, только когда ей требуются *новые данные извне*. Сравнение, выбор, рассуждение по уже полученным данным модель делает внутри текущего ответа.

Пример: «погода в Париже, Лионе и Ницце + что надеть в самом холодном» = **2 запроса** (запрос → 3 параллельных tool call → результаты обратно → модель сама находит минимум и советует одежду).

## Безопасность: tool call — недоверенный ввод

Разделение «модель предлагает — код решает» — это **граница безопасности (security boundary)**.

- Модель не знает прав пользователя и контекста безопасности — она генератор текста.
- Код обязан **валидировать** tool call перед исполнением: права пользователя, разумность аргументов.
- Угрозы: злонамеренный пользователь и **prompt injection** (вредоносный текст в данных, которые читала модель).
- Модель никогда не исполняет сама → «обманутая» модель не сможет сделать то, что код откажется выполнять.

---

## Function calling vs structured outputs vs JSON mode

Все три стоят на одной способности модели — следовать схеме:

| Механизм | Что делает | Кто исполняет код |
|---|---|---|
| Structured outputs | ответ в фиксированной форме данных | никто — просто ответ |
| JSON mode | ответ — только валидный JSON (без гарантии схемы!) | никто — просто ответ |
| Function calling | JSON-**запрос** на вызов функции | ваше приложение |

«Function calling — это structured output, поставленный на работу».

Дополнительно: `strict: true` в схеме **гарантирует** соответствие аргументов схеме (не «best effort»); enum превращает «свободное поле» в «выпадающий список».

---

## Function calling — основа агентов

**AI-агент** — система, которая не просто общается, а достигает цели действиями; действия = tool calls. Агентный цикл (agent loop): модель → tool call → исполнение → результат → модель → … пока цель не достигнута.

Примеры цепочек: `search_flights → book_flight → send_confirmation_email`; `read_file → edit_file → run_tests`.

**MCP (Model Context Protocol)** — открытый стандарт описания инструментов один раз для переиспользования в разных AI-приложениях.

## Расхождения и оговорки источников

- **Нумерация 5 шагов**: OpenAI считает от API-запроса; Outcome School — от описания функций. Суть идентична, в конспекте — версия OpenAI.
- **Формат `arguments`**: в статье Outcome School показан как готовый JSON-объект; в реальном API OpenAI это JSON-**строка** (нужен `json.loads`).
- **JSON mode ≠ схема**: гарантирует валидный JSON, но не соответствие вашей схеме (это structured outputs / strict mode).
- **«Меньше 20 функций»** — мягкая рекомендация OpenAI, не закон.
- Старые туториалы (2023–2024) используют устаревший синтаксис (`functions` вместо `tools`, Chat Completions) — концепция та же.
