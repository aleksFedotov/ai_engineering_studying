## 1. Базовый словарь

| Термин | Что это |
|---|---|
| Инструмент / функция (tool / function) | Декларация возможности для модели: имя, описание, JSON-схема параметров. Модель видит только описание — код ей недоступен |
| Вызов инструмента (tool call) | Особый тип *ответа* модели: «вызови X с аргументами Y». Модель **ничего не исполняет** |
| Результат вызова (tool call output) | Строка (JSON/текст/ошибка), которую возвращает твой код, обязательно со ссылкой на вызов через `call_id` (OpenAI) / `tool_use_id` (Anthropic) |
| Агентный цикл (agentic loop) | Цикл «запрос → вызов(ы) → исполнение → результат → повторный запрос», пока модель не ответит текстом |

**Ключевая ментальная модель:** модель — диспетчер, который *просит*; твой код — руки, которые *исполняют*. Аргументы модели — недоверенный ввод (untrusted input).

## 2. Эталонный цикл (Responses API)

```python
input_list += response.output                     # вызовы остаются в истории!

for tool_call in response.output:                 # ноль / один / МНОГО — всегда циклом
    if tool_call.type != "function_call":
        continue
    args = json.loads(tool_call.arguments)        # arguments — строка с JSON!
    result = call_function(tool_call.name, args)  # роутер по имени (словарь)
    input_list.append({
        "type": "function_call_output",
        "call_id": tool_call.call_id,             # сопоставление вызов ↔ результат
        "output": json.dumps(result),             # один dumps, не два!
    })

response = client.responses.create(model=..., tools=tools, input=input_list)  # повторный запрос
```

Критерии цикла while:
- **OpenAI Responses:** `while any(item.type == "function_call" for item in response.output)`
- **Anthropic:** `while response.stop_reason == "tool_use"`
- **Всегда:** счётчик итераций (MAX_STEPS) — защита от зацикливания «вызов → ошибка → тот же вызов».

Роутер словарём (расширяемо, неизвестное имя → ошибку модели, не raise):

```python
ROUTER = {"query_sql": query_sql, "get_customer_profile": get_customer_profile}

def call_function(name, args):
    fn = ROUTER.get(name)
    if fn is None:
        return {"error": f"unknown function: {name}"}
    return fn(**args)
```

## 3. Два API OpenAI + Anthropic — три силуэта

| | OpenAI Responses | OpenAI Chat Completions | Anthropic |
|---|---|---|---|
| Определение | плоско: `type/name/description/parameters/strict` | `type: "function"` + вложенный `function: {...}` | `name/description/input_schema` (без type) |
| Аргументы | `item.arguments` — строка → `json.loads` | `tool_call.function.arguments` — строка | `block.input` — готовый dict |
| ID вызова | `item.call_id` | `tool_call.id` | `block.id` (`toolu_...`) |
| Результат | `{"type": "function_call_output", "call_id": ...}` в input | сообщение `role: "tool"` | блок `tool_result` с `tool_use_id` в `role: "user"` (+ `is_error: true` для сбоев) |
| Стоп-критерий | функциональные элементы в `response.output` | `finish_reason == "tool_calls"` | `stop_reason == "tool_use"` |

**Правило:** в проекте — один протокол. Любой сниппет из интернета сначала классифицировать: `functions/function_call` (доисторический, deprecated с 2023-12), `chat.completions` (зрелый), `responses` (современный).

## 4. tool_choice — шкала контроля

| Режим | OpenAI | Anthropic | Когда |
|---|---|---|---|
| Авто (дефолт) | `"auto"` | `{"type": "auto"}` | обычный диалог |
| Обязательно хоть один | `"required"` | `{"type": "any"}` | каждый шаг должен дать структурированное действие (роутер тикетов) |
| Принудительно конкретный | `{"type": "function", "name": "..."}` | `{"type": "tool", "name": "..."}` | LLM как типизированная функция (извлечение данных) |
| Подмножество | `{"type": "allowed_tools", ...}` | — | мультитенантность, prompt caching |
| Запрет | `"none"` | `{"type": "none"}` | финальный ответ, суммаризация |

Опасности принудительного режима в цикле:
1. У Anthropic prefill отключает текст перед `tool_use` — модель не объяснит действия.
2. В while-цикле forced-вызов будет приходить на каждом шаге → бесконечный цикл (лечение: счётчик итераций).

## 5. Strict mode (Structured Outputs)

- `strict: true` гарантирует соответствие аргументов схеме (не «best effort»).
- Требования: `additionalProperties: false` + все поля в `required` (опциональность через `"type": ["string", "null"]`).
- **Не проверяет:** `pattern`, `format`, `minLength`, `minimum` и т.п. — форма гарантирована, содержимое валидируй в коде.
- JSON mode (`json_object`) ≠ Structured Outputs: первый — только валидный JSON, legacy.
- Продакшен-контракт из трёх проверок: 1) поле `refusal`? 2) обрезан ответ (`finish_reason`)? 3) иначе вывод соответствует схеме.
- У **fine-tuned** моделей strict отключается для параллельных вызовов (офиц. гайд; статья Stackademic утверждает шире — расхождение, верить официальному гайду).
- Генерация схем из Pydantic/Zod вместо ручного JSON — страховка от структурных багов.

## 6. Параллельные вызовы (parallel function calling)

- Модель может вернуть несколько вызовов за один ответ; `parallel_tool_calls: false` → ноль или один. По умолчанию включён.
- Выигрыш: латентность (время ≈ самый медленный вызов вместо суммы; 3 последовательных round-trip — 6–9 с).

### Когда параллелизм вреден (итоговый список)

1. **Зависимые вызовы** — аргумент второго известен только после первого (customer_id → заказы).
2. **Гонки побочных эффектов** — мутация vs мутация (transfer до freeze), мутация vs чтение (чтение вернёт «до» или «после» недетерминированно).
3. **Strict-режим у fine-tuned моделей** отключается при параллельных вызовах.
4. **Деструктивные действия** — не параллелить никогда; паттерн prepare → confirm → execute (напр. `prepare_refund` → подтверждение пользователя → `execute_refund`).
5. **(найдено экспериментально)** Сравнительные вопросы на слабых моделях: синтез над однотипными параллельными результатами ненадёжен (gpt-4o-mini перепутал «Анна: 3, Иван: 1» местами при верных данных). Надёжнее один агрегирующий GROUP BY.

**Почему заморозку карты нельзя параллелить (контрольная точка):** зависимость по данным (нужен card_id) + гонка с другими мутациями (деньги могут уйти до блокировки) + деструктивность (нужен человек в петле). Механизмы: `parallel_tool_calls=false`, отдельный оборот цикла, prepare/execute, валидация владения ресурсом на бэкенде.

## 7. Обработка ошибок

- Исключение в функции ≠ исключение в программе: `try/except` → текст ошибки как tool-результат → модель исправляет аргументы или честно признаёт проблему.
- Anthropic: `tool_result` с `is_error: true`.
- Проверено вживую: `SecurityError` про таблицу `payments` → модель честно ответила и предложила альтернативу. ✅

### Три класса отказов (наблюдены в экспериментах)

1. **Громкая ошибка** — `error` в результате; модель корректируется. Легко ловится.
2. **Стохастический синтез** — данные верны, финальный текст перепутал факты. Лечится: агрегирующий запрос, последовательность вместо параллели, модель посильнее.
3. **Тихий фейл** — `success` с пустым `data` из-за плохого запроса (регистр: `'наушники'` vs `'Наушники'`); модель ответила «нет данных», хотя они есть. Лечится: подсказка в description («If 0 rows — retry with LIKE / other casing») или `hint` в ответе инструмента. **Пустой результат ≠ отсутствие данных.**

## 8. Best practices при определении инструментов

- Описание = документация: 3–4 предложения, «что делает / когда использовать / когда НЕ использовать / что НЕ возвращает». Главный рычаг качества выбора инструмента.
- Включать схему данных в description (колонки, допустимые значения enum-полей) — иначе модель угадывает имена.
- Пример в описании параметра — самая весомая подсказка; ошибка в нём заразит все вызовы.
- Не заставлять модель заполнять то, что код знает сам (db_path, user_id из сессии).
- Тест стажёра: мог бы человек правильно вызвать функцию, видя только её описание?
- Консолидация: объединять последовательные вызовы (OpenAI) / операции через параметр `action` (Anthropic).
- Мало инструментов: <20 мягко (OpenAI), <10 если важна точность (Stackademic); описания жгут input-токены на каждом запросе.
- Неймспейсинг имён: `db_query_sql`, `github_list_prs`.
- High-signal ответы инструментов: только нужные поля, LIMIT + флаг `truncated`.
- Anthropic `input_examples` — валидируемые примеры входов (20–200 токенов каждый; для сложных входов).
- Определения инструментов — API-контракт: версионировать, не переименовывать без тестов; новый инструмент может изменить выбор для старых промптов → прогонять evals.
- Системный промпт — для ролей и границ («Use tools when... / Do not use tools when...»), не для дублирования схем.

## 9. Терминология и история

- Июнь 2023: `functions` + `function_call` (без параллелизма). Конец 2023: `tools` + `tool_choice`, старые — deprecated.
- Словарь провайдеров: OpenAI — function/tool calling; Anthropic — tool use; Google — function calling; Microsoft — tool calling. Механика одна.
- `previous_response_id` (Responses API) — серверное состояние диалога вместо ручной истории; tools подтягиваются автоматически. Для отладки прозрачнее клиентская история.

## 10. Типовые грабли в коде (из своих ошибок)

1. Пропущенная запятая в многострочном dict → implicit string concatenation склеивает строки и ломает структуру молча. Лечение: `"""тройные кавычки"""` для описаний.
2. `required` / `additionalProperties` должны лежать в `parameters` рядом с `properties`, не внутри него (иначе 400: «['query'] is not of type 'object'»).
3. `strict` — на уровне функции, рядом с `name`.
4. `response.output` — список: итерироваться, не `response.output.name`.
5. Двойной `json.dumps` результата → экранированная строка вместо JSON.
6. Внутри while — обязательно повторный запрос к модели, иначе цикл крутит старый ответ до MAX_STEPS.
7. LIMIT-подстановка: свой `LIMIT 10` от модели обходит твой MAX_LIMIT → оборачивать запрос: `SELECT * FROM (<запрос>) LIMIT N+1`.
8. Белый список таблиц по токенам — эвристика (проверяет первое вхождение from/join), второй слой после read-only соединения.

## 11. Что сделано на практике (SQLite-агент)

- База `shop.db`: customers (6 строк), orders (7 строк); ловушки: Ольга без заказов, отменённый заказ Марии, 'Наушники' с заглавной.
- Инструменты: `query_sql` (SELECT-only, белый список, LIMIT/truncated) + `get_customer_profile` (точечный lookup).
- Наблюдения: зависимые вызовы модель сама сериализует; параллельные вызовы — 2 вызова за шаг (parallel on) vs 4 шага (parallel off, но надёжнее синтез); выбор инструмента управляется описаниями; обработка ошибок работает (payments, «клиент не найден»).
