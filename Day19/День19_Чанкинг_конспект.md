## 1. Зачем нужен чанкинг (chunking)

RAG-пайплайн (retrieval-augmented generation) не может подать документ в эмбеддинг-модель целиком — у моделей **лимит токенов (token limit)**. Документы режутся на чанки (chunks), каждый превращается в вектор (embedding), векторный поиск (vector search) достаёт только релевантные куски.

**Три режима отказа:**
- Чанки **слишком мелкие** → нет контекста, ответы нерелевантны.
- Чанки **слишком крупные** → смысл «размывается» (context dilution), дороже, шумнее.
- **Плохие границы** → смысл разорван посреди предложения, эмбеддинг «усреднённый».

**Ключевой механизм:** эмбеддинг *усредняет* смысл всего чанка в один вектор. Несколько тем в чанке → вектор «между темами» → падает косинусное сходство (cosine similarity) с любым конкретным запросом → чанк не попадает в топ-K → LLM отвечает плохо. **Смена эмбеддинг-модели это не лечит** (garbage in, garbage out).

**Исследование Vectara (NAACL 2025, arXiv:2410.13070):** конфигурация чанкинга влияет на качество поиска **не меньше, чем выбор эмбеддинг-модели** (25 конфигураций × 48 моделей). Сначала настраивай чанкинг, потом модель.

## 2. Семь стратегий чанкинга

| # | Стратегия | Суть | Когда | Минусы |
|---|---|---|---|---|
| 1 | **Fixed-size** (фиксированный размер) | Равные сегменты, шаг `size - overlap` | Логи, код, однородные данные; бейзлайн | Режет предложения, игнорирует смысл |
| 2 | **Recursive** (рекурсивный) ⭐ДЕФОЛТ | Иерархия сепараторов: абзац → строка → слово → символ | Почти всё: статьи, документация, базы знаний | Всё ещё «слепой» к смыслу; чанки неравномерны |
| 3 | **Sentence-level / Language-based** (по предложениям) | NLP-разбиение по предложениям (spaCy, NLTK), группировка до размера | Проза, юридические, нарративные тексты | Длинные предложения могут превысить лимит; не видит смену темы |
| 4 | **Document-aware / Context-aware** (по структуре) | Границы по структуре: Markdown-заголовки, HTML-теги, страницы PDF, функции в коде + метаданные | Доменный RAG, документы с явной структурой | Нужны метаданные и доменные правила; больше инженерии |
| 5 | **Semantic** (семантический) | Эмбеддинги предложений; косинусное сходство **соседних** предложений; граница там, где сходство падает ниже порога | Мультитематические документы, дорогой ingestion допустим | Дорого, сложно настраивать; **НЕ стабильно лучше рекурсивного** |
| 6 | **LLM-based** (чанкинг через LLM) | LLM размечает семантически завершённые единицы | Мало документов + высокая ценность (контракты) | На порядки дороже; не масштабируется |
| 7 | **Late chunking** (поздний чанкинг) | **Сначала эмбеддим документ ЦЕЛИКОМ, потом режем эмбеддинги** — каждый вектор «знает» контекст (местоимения, ссылки «см. п. 3») | Плотные перекрёстные ссылки; юр./тех. документы | Требует длинноконтекстной эмбеддинг-модели; для обычной прозы выигрыш маргинален |

> ⚠️ **Late chunking ≠ «резать с конца документа»**. Порядок: embed → split, а не split с конца.

### Эскалация выбора стратегии

```
Есть структура/метаданные?  → context-aware / document-aware
Нет структуры, нужна точность, есть бюджет? → semantic (с min_chunk_size!)
Мало ценных документов?     → LLM-based
Плотные перекрёстные ссылки? → late chunking
Короткие самодостаточные документы (FAQ 200–300 слов)? → НЕ чанкать вообще
Всё остальное               → RECURSIVE (дефолт)
```

## 3. Цифры из бенчмарков (источник №2, PremAI)

**Дефолт-мантра: «Recursive, 512 токенов, overlap 50–100»** — 69% точности во FloTorch, лучший результат, ноль вызовов модели, миллисекунды работы.

| Правило | Значение | Источник |
|---|---|---|
| Базовый диапазон | **256–512 токенов** | бенчмарк-консенсус |
| Аналитические / multi-hop запросы | **512–1024 токенов** | NVIDIA 2024 |
| Финансовые документы | 1024 токена → 57.9% (лучше мелких) | NVIDIA, FinanceBench |
| Overlap | **10–20%** (Azure: до 25% = 128 токенов) | Microsoft Azure |
| «Обрыв контекста» (context cliff) | ~2500 токенов — дальше качество падает | Firecrawl, янв. 2026 |
| Короткие FAQ (200–300 слов) | чанкинг **вредит** — документ целиком | Firecrawl |

### Парадокс семантического чанкинга: 91.9% vs 54%

- **Chroma** мерил retrieval recall (нашёлся ли релевантный текст) → 91.9%, лучший.
- **FloTorch** мерил сквозную точность ответа (end-to-end answer accuracy) → 54%, на 15 пунктов хуже рекурсивного (69%).
- **Причина:** фрагменты в среднем **43 токена** — ретривятся чисто, но LLM не хватает контекста ответить.
- **Вывод 1:** сквозные метрики важнее retrieval-only. «Хорошо ретривится, плохо отвечает» = плохой чанк.
- **Вывод 2:** при семантическом чанкинге `min_chunk_size=200–400` **обязателен**.
- **Вывод 3:** Vectara (рецензируемое): fixed-size стабильно обгонял semantic на реалистичных данных. Самая частая ошибка — брать semantic «по умолчанию, потому что звучит principled».

> 🔗 Блок для памяти: **«43 токена / 54% / min_chunk_size 200–400»**.

**Почему плохи чанки ~128 токенов:** тот же механизм, что у 43-токенных — ретривятся, но содержат ключевые слова ответа, а не **полный ответ**; LLM не из чего рассуждать.

## 4. Официальный API LangChain (источник №3, доки)

### Три категории сплиттеров (официальная таксономия)

| Категория | = стратегия из статей |
|---|---|
| **Text structure-based** | recursive |
| **Length-based** (token-based / character-based) | fixed-size |
| **Document structure-based** (Markdown/HTML/JSON/code) | context-aware |

Semantic / LLM-based в базовый пакет `langchain-text-splitters` **не входят** — живут в сторонних библиотеках (LlamaIndex, Chonkie).

### RecursiveCharacterTextSplitter

- Дефолтные сепараторы: `["\n\n", "\n", " ", ""]` — **без `". "`** (уровень предложений в дефолте отсутствует, это кастомизация из статей).
- Параметры: `chunk_size`, `chunk_overlap`, `length_function` (единицы измерения!), `is_separator_regex`.
- `.split_text(str)` → список строк; `.create_documents([str])` → объекты `Document` с метаданными (для реального пайплайна).
- По умолчанию меряет **символы** (`length_function=len`)!

### Размер в токенах

**Правило доков: считай токены тем же токенизатором, что у целевой модели** (у разных моделей разные BPE-словари; чужой токенизатор даёт ошибку 10–20%).

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

# РЕКОМЕНДУЕМЫЙ способ — жёсткий лимит в токенах:
splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    encoding_name="cl100k_base",   # или model_name="gpt-4"
    chunk_size=512,
    chunk_overlap=50,
)
chunks = splitter.split_text(text)
```

- `CharacterTextSplitter.from_tiktoken_encoder` — лимит **мягкий** (режет по одному сепаратору, токены только измеряет; длинный кусок может превысить лимит).
- `RecursiveCharacterTextSplitter.from_tiktoken_encoder` — лимит **жёсткий** (переросший чанк рекурсивно дробится).
- `TokenTextSplitter` — режет прямо по токенам, но для китайского/японского может **разорвать многобайтовый иероглиф** → битый Unicode. Там — только `.from_tiktoken_encoder`.
- Альтернативы: `from_huggingface_tokenizer` (любая HF-модель), `SentenceTransformersTokenTextSplitter` (под окно эмбеддинг-модели).

### Почему токены, а не символы 🎯 (контрольная точка)

1. Потребитель чанка — эмбеддинг-модель, её лимит задан **в токенах**.
2. Символы — плохой прокси: английский ~4 символа/токен, **русский ~2–3** (проверено на практике: 2,37), код — своя картина. «512 символов» русского текста ≈ 215 токенов.
3. Токенизатор должен совпадать с токенизатором модели.

## 5. Практика: два сплиттера, сравнение на одном тексте

Текст: «Машинное обучение: от данных к предсказаниям» (~2240 токенов, ~5300 символов).

### Свой фиксированный сплиттер (токены, overlap)

```python
import tiktoken
encoder = tiktoken.get_encoding("cl100k_base")

def fixed_size_chunking(text, size=512, overlap=50):
    if overlap >= size:
        raise ValueError("overlap должен быть строго меньше size")
    tokens = encoder.encode(text)
    return [encoder.decode(tokens[i:i + size])
            for i in range(0, len(tokens), size - overlap)]
```

### Результаты

| | Fixed | Recursive |
|---|---|---|
| Чанков | 5 | 6 |
| min / max / avg (токены) | 394 / 512 / 488 | 185 / 489 / 379 |

**Границы:** fixed разорвал слово («линейная регрессия, **л**» | «**атегориальна**...»), recursive закончил чанк на границе предложения («...это классификация.»). Recursive «недобирает» до лимита — это цена за целостные границы, не баг.

### Баги, найденные в первой версии (на память)

1. Цикл шёл по `len(text)` (символы) вместо `len(tokens)`; `decode()` ждёт id токенов, не строку.
2. Сплиттер не callable — нужен `.split_text()`.
3. `len_sum += len_sum` вместо `len_sum += chunk_len`.
4. `main()` не вызывался (нужен `if __name__ == "__main__": main()`).
5. Статистику стоит считать в токенах, а не символах.

## 6. Расхождения источников (чему верить)

| Тема | Источник №1 (Medium) | Источник №2 (PremAI) + №3 (доки) | Верить |
|---|---|---|---|
| Размер чанка | 200–500 токенов | 256–512, аналитика 512–1024 | №2 (бенчмарки) |
| Semantic chunking | «максимизирует точность», кластеризация всех предложений | «не стабильно лучше», сходство соседних предложений | №2 |
| Импорт | `from langchain.text_splitter` (устарел) | `from langchain_text_splitters` | №3 (доки) |
| Дефолтные сепараторы | `["\n\n","\n",". "," ",""]` | `["\n\n","\n"," ",""]` | №3 (доки) |

Консенсус всех источников: **дефолт = рекурсивный, начинаем с него и измеряем**.

## 7. Шпаргалка «одной строкой»

- Дефолт: **recursive, 512 токенов, overlap 50–100 (10–20%)**.
- Меряем в **токенах**, токенизатор = токенизатор модели (`from_tiktoken_encoder`).
- Semantic — только с `min_chunk_size=200–400` и после того, как recursive измерен и не хватило.
- Короткие документы (FAQ) **не чанкать**.
- Финансы/PDF с таблицами → page-level или 1024; не резать таблицы.
- Оценивать **сквозной** точностью ответа, не только retrieval recall.
- «Начни с простого, измерь, потом оптимизируй».
