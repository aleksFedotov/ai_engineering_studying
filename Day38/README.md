# День 38 — оценка RAG

Скрипт использует `Day35.project_week_5.call_client`, сбрасывает историю перед каждым
вопросом и собирает тексты из настоящих результатов `search_documents` и
`search_in_document`. Агент дня 35 проверяет необходимость поиска и финализирует ответ после лимита инструментов. `relevant_chunks` из eval-набора
не используется как извлечённый контекст. Сохраняются все поисковые вызовы,
их порядок и повторы; модель получает полный текст каждого чанка.

## Запуск из корня проекта (Bash)

Нужны зависимости предыдущих дней, API-ключи в `.env`, Qdrant на
`http://localhost:6333` и готовая hybrid-коллекция. Импорт дня 28 также создаёт
Anthropic-клиент и загружает модели поиска. Скрипт не создаёт индексы.

```bash
python -m pip install -r Day38/requirements.txt

# Сначала короткий прогон; вызовы RAG и судьи используют API.
python Day38/eval_rag.py --limit 2 --out Day38/out_data/smoke

# Все 37 вопросов, baseline 512.
python Day38/eval_rag.py

# Повторная оценка сохранённых ответов без повторного вызова RAG.
python Day38/eval_rag.py --stage evaluate

# Только сбор ответов, без RAGAS.
python Day38/eval_rag.py --stage collect --out Day38/out_data/collect_only

# Вариант 256: предварительно проверь наличие коллекции и соответствие корпуса.
python Day38/eval_rag.py --collection chunks_256_hybrid --chunks Day27/data/chunks_256.jsonl --out Day38/out_data/variant_256

python Day38/eval_rag.py --stage compare --baseline Day38/out_data/baseline_512 --variant Day38/out_data/variant_256 --out Day38/out_data/comparison
```

Для чистого эксперимента оба индекса должны быть построены из одного корпуса
с одинаковыми моделями эмбеддингов, схемой dense/sparse и обработкой текста;
меняется только размер чанков. Коллекция дня 27 приведена как доступный в коде
вариант, её соответствие baseline автоматически не гарантируется.

Повторный сбор в ту же папку запрещён, чтобы не потерять ответы. Для нового
прогона укажи новый `--out`. Можно оценивать внешний файл через `--runs`.

## Результаты

- `config.json` — настройки генерации и индекс.
- `runs.jsonl` — ответы, фактический контекст, инструменты и ошибки; пишется после каждого вопроса.
- `scores.jsonl` / `scores.csv` — оценки по вопросам.
- `summary.json` — средние, число успешных оценок и пропусков.
- `delta.json` — разница variant минус baseline по одинаковым успешно оценённым парам.

Faithfulness и answer relevancy считаются для всех полученных ответов.
Context precision, context recall и answer correctness — только при наличии
непустого golden answer. Ошибка генерации и невычисленная метрика сохраняются
как null, не как ноль. Средние всегда читай вместе с количеством scored/missing.
Отказы и пустой контекст не исключаются автоматически: некоторые метрики могут
быть не определены. Детали ошибок RAGAS выводятся библиотекой в консоль.

## Интерпретация

| Метрика | Что оценивает |
|---|---|
| faithfulness | Поддерживаются ли утверждения ответа фактически переданным контекстом |
| answer relevancy | Соответствует ли ответ вопросу; не проверяет правильность фактов |
| context precision | Насколько релевантные найденные фрагменты находятся выше в выдаче |
| context recall | Насколько найденный контекст покрывает утверждения эталонного ответа |
| answer correctness | Соответствие ответа эталону по фактам и семантической близости |

Высокий precision при низком recall — повод проверить top-k и чанкинг;
низкий precision при высоком recall — ранжирование и лишние фрагменты;
низкие оба — корпус, запросы, эмбеддинги и поиск. Это гипотезы для проверки,
а не однозначные диагнозы. Высокий faithfulness при низком correctness может
указывать на неполный/неверный контекст, неполный ответ или проблему эталона.
Для agentic RAG precision здесь относится к объединённой последовательности
всех поисковых результатов, а не к одной выдаче ретривера.

Зависимости оценки закреплены в `requirements.txt`: RAGAS 0.4.3 и
langchain-openai 1.6.7; используются обёртки LangChain.
Общий конспект задания находится рядом в файле «День 38 — Конспект. Метрики RAG (RAGAS).md».

Текущий агент сначала строит план запроса, затем выполняет обязательный поиск
для каждого запроса. Поле `requires_document_search` остаётся в структурированном
ответе, но не отменяет начальный поиск. Черновики содержат части вопроса и факты
с привязкой к `source_id`; цитаты подставляются из полных результатов поиска.
После MAX_STEPS раундов выполняется отдельный запрос с tool_choice="none".
Это предотвращает потерю ответа только из-за лимита; сбой API всё ещё может дать no_answer.
Новые прогоны сохраняй в другую папку: старый baseline использовал обрезку 800 символов,
поэтому сравнение старого baseline с новым вариантом уже не изолирует влияние чанкинга.

## Проблемные случаи и ограничения

`problem_cases.jsonl` содержит шесть вопросов для проверки частичных ответов,
неподтверждённых предпосылок, неоднозначности и различения одноимённых людей.
Каталоги `out_data/problem_cases_v5`–`problem_cases_v11` сохраняют историю
экспериментов, включая неудачные версии; это не отдельные тестовые сплиты.

В v11 получено 3 ответа из 6. Атия, Помпей Младший и Mars завершились ошибкой
валидации сущности после попытки исправления. Совпадение имени в тексте не
гарантирует, что источник подтверждает конкретное утверждение; буквальная
проверка может также отклонить допустимую формулировку. Эти проблемы ещё не решены.
Средние метрики v11 рассчитаны только по трём сохранённым ответам и не означают
улучшение относительно версий с большим количеством полученных ответов.

Локальные проверки управления агентом и валидации без вызовов API:

```bash
python -m unittest Day35.test_client_control -q
```

Тесты проверяют конкретные сохранённые случаи и ограничения кода, но не
гарантируют качество новых ответов модели. Дополнительные проверки по сохранённым
v9/v10 запускаются при наличии соответствующих файлов результатов.
