## 1. Зачем RAG нужны свои метрики

- BLEU/ROUGE сравнивают n-граммы с одним эталоном — для RAG бесполезны: разные формулировки могут быть верны, а гладкий ответ — выдуман.
- RAGAS использует **LLM-as-a-judge** (LLM-судья): судья разбивает тексты на утверждения (claims) и верифицирует их.
- **Две поверхности отказа (two failure surfaces):** ретривер (плохой/неполный контекст) и генератор (игнорирует контекст, додумывает). Сквозная метрика их не различает → нужны компонентные метрики.
- «Тихие отказы» (silent failures): чем сильнее модель, тем убедительнее она галлюцинирует.

### Входные поля датасета оценки

| Поле | Что это |
|---|---|
| `user_input` | вопрос пользователя |
| `response` | сгенерированный ответ |
| `retrieved_contexts` | список извлечённых чанков (chunks) |
| `reference` | эталонный ответ (golden answer) — нужен не всем метрикам |

## 2. Четыре базовые метрики

### 2.1 Faithfulness (достоверность) — генерация, reference-free

> Ответ «достоверен», если **все** его утверждения выводимы из контекста.

**Алгоритм:** разбить ответ на утверждения → проверить каждое против `retrieved_contexts` → доля подтверждённых.

```
Faithfulness = (утверждений ответа, подтверждённых контекстом) / (всего утверждений в ответе)
```

- 0.95 = 95% утверждений ответа подтверждены контекстом.
- **Не знает «правду мира»:** если контекст неверен, а модель его повторила — faithfulness = 1.0 при фактически неверном ответе.
- Reference-free → можно гонять на живом продакшен-трафике (guardrail-метрика).
- Вариант `FaithfulnesswithHHEM`: верификация claims классификатором Vectara HHEM-2.1-Open вместо LLM (дёшево, для прода).

### 2.2 Answer Relevancy (релевантность ответа) — генерация, reference-free

> Насколько ответ отвечает на вопрос (соответствует интенту). **Не** оценивает фактическую точность. Штрафует неполноту и лишние детали.

**Механика RAGAS («обратная генерация вопроса»):**
1. LLM генерирует N искусственных вопросов (по умолчанию 3, параметр `strictness`), на которые `response` был бы ответом.
2. Косинусное сходство (cosine similarity) эмбеддинга исходного вопроса (E_o) с каждым сгенерированным (E_gi):

```
Answer Relevancy = (1/N) · Σᵢ cos(E_gi, E_o) = (1/N) · Σᵢ (E_gi·E_o)/(‖E_gi‖‖E_o‖)
```

- Идея: если ответ по делу, исходный вопрос восстановим из ответа.
- Диапазон «не гарантированно» [0,1]: у косинусного сходства он [−1, 1].
- **Слепа к галлюцинациям** → смотреть в паре с faithfulness.
- Низкий score → обычно проблема промпта (многословие, уклончивость) ИЛИ извлечён не тот контент (см. раздел 5).

> ⚠️ В DeepEval метрика с тем же именем считается иначе: доля утверждений ответа, классифицированных как релевантные. Числа RAGAS и DeepEval несравнимы.

### 2.3 Context Precision (точность контекста) — ретрив

> Способность ретривера ставить релевантные чанки **выше** нерелевантных (качество ранжирования).

```
Context Precision@K = Σₖ (Precision@k · vₖ) / (число релевантных чанков в top-K)
Precision@k = TP@k / (TP@k + FP@k),  vₖ ∈ {0,1} — индикатор релевантности на позиции k
```

- Взвешенная схема ≈ Average Precision из информационного поиска: релевантный чанк на 1-й позиции «стоит» больше, чем на 8-й.
- Перестановка [релевантный, нерелевантный] → [нерелевантный, релевантный]: score 1.0 → 0.5.
- Низкий precision = шум в генерации → риск «заякорить» модель на мусоре.
- Семейство вариантов: `ContextPrecision` (против reference), `ContextUtilization` (против response, ref-free), non-LLM (rapidfuzz), ID-based.

### 2.4 Context Recall (полнота контекста) — ретрив, требует reference

> Какая доля нужной информации извлечена. Про «не пропустить важное».

```
Context Recall = (утверждений эталона, подтверждённых контекстом) / (всего утверждений в эталоне)
```

- **Зеркальна faithfulness:** у faithfulness числитель/знаменатель — про ответ; у recall — про эталон; проверка в обоих случаях по контексту.
- `reference` — прокси для «истинно релевантных чанков» (reference_contexts), т.к. разметка чанков дорога.
- Побочный эффект: если эталон содержит то, чего нет в корпусе, recall не достигнет 1.0 (и это не вина ретривера).
- Причины провалов: чанкинг, согласование эмбеддингов (embedding alignment), недостаточный top-k.

### 2.5 Factual Correctness (фактическая корректность) — end-to-end, требует reference

> Сравнение `response` с `reference` по фактам. Оба → claims → перекрытие через NLI.

```
TP = утверждения ответа, есть в эталоне;  FP = утверждения ответа, нет в эталоне;  FN = утверждения эталона, нет в ответе
Precision = TP/(TP+FP);  Recall = TP/(TP+FN);  F1 = 2PR/(P+R)   (параметр mode, по умолчанию f1)
```

- Гранулярность claims: `atomicity` (мелкость дробления), `coverage` (полнота покрытия).

> ⚠️ **Замена названия:** в старых версиях RAGAS (и в статьях №2–3) — `AnswerCorrectness` (claim-overlap + semantic similarity). В актуальной документации — `FactualCorrectness`. Роль в диагностике та же.

### Сводная таблица

| Метрика | Что мерит | Нужен reference? | Диагностирует |
|---|---|---|---|
| Faithfulness | Ответ grounded в контексте? | Нет | Генерацию |
| Answer Relevancy | Ответ по теме вопроса? | Нет | Генерацию (промпт) |
| Context Precision | Релевантные чанки наверху? | Да (или ref-free) | Ретрив (ранжирование) |
| Context Recall | Всё нужное извлечено? | Да | Ретрив (покрытие) |
| Factual Correctness | Ответ совпадает с эталоном? | Да | End-to-end |

## 3. Диагностика по комбинациям (КОНТРОЛЬНАЯ ТОЧКА ДНЯ)

### Таблица 2×2: precision × recall

| Context Precision | Context Recall | Диагноз | Что чинить |
|---|---|---|---|
| Высокий | Высокий | Ретрив здоров | Фокус на генерацию |
| Низкий | Высокий | Нужное извлечено, плохо отранжировано | **Реранкинг** |
| Высокий | Низкий | Топ чистый, информации не хватает | **top-k ↑ или размер чанка ↑** |
| Низкий | Низкий | Ретривер fails broadly | **Эмбеддинги / индексация** |

### Пары метрик

| Сигнатура | Диагноз |
|---|---|
| Высокий faithfulness + низкая correctness | Пробел ретрива/корпуса (ответ верен контексту, неверен по факту) → смотри context recall; промпт бесполезен |
| Низкий faithfulness + высокий recall | Контент есть, модель от него уходит → промпт/генератор |
| Высокий faithfulness + низкая relevancy | Неоднозначно: либо промпт (QASkills), либо не тот контент (Atlan). Разводить по precision: низкий → контент; высокий → промпт |
| Все четыре высокие | Пайплайн здоров на уровне инференса (но см. пятое измерение, раздел 6) |

## 4. Инженерные практики (из источника №2)

**Настройка судьи**
- Дешёвая быстрая модель (gpt-4o-mini) для больших прогонов; сильная — для спот-проверок.
- **Модель-судья фиксируется между прогонами** — иначе score несравнимы во времени.
- Локальный судья через Ollama (приватно, бесплатно) — но шумнее; валидировать на подвыборке против хостед-модели.

**Датасет**
- 50–100 курированных примеров: типовые запросы + edge cases + **вопросы, на которые корпус ответить не может**.
- Synthetic-then-curated: `TestsetGenerator` генерирует черновик из ваших документов (simple / multi-hop / conditional) → ручная выбраковка и правка reference.

**Прогон**
- Один `evaluate(dataset, metrics=[...])` считает всё, параллелит (`RunConfig(max_workers=8)`), результат → pandas.
- Сортировка по faithfulness ↑ = очередь подозрительных на галлюцинации ответов.

**CI/CD quality gate**
- Пороги чуть **ниже** текущего baseline (ловим регрессии, не шум).
- Подвыборка на PR, полный датасет — ночной прогон.

**Трекинг**
- Каждый прогон → строка в JSONL (timestamp + commit hash + средние метрики) → тренды против истории изменений.

**Типичные ошибки**
1. Доверять одному прогону (у LLM-судьи дисперсия → 2–3 прогона, смотреть разброс).
2. Незафиксированный/слабый судья.
3. Датасет из 10 happy-path вопросов.
4. Гнаться за 1.0: «0.9 с хорошим покрытием > 1.0 на тривиальном датасете. Метрики — компас, не табло».

## 5. Расхождения между источниками

1. **API:** документация (№1) рекомендует `ragas.metrics.collections` (legacy `SingleTurnSample` deprecated, удалят в v1.0). Статья №2 — вся на legacy API. Код №3 — синтаксис ~0.1.x, копировать нельзя.
2. **Answer Correctness → Factual Correctness** (см. 2.5).
3. **Answer Relevancy: две механики** — RAGAS (обратные вопросы + косинусное сходство) vs DeepEval (доля релевантных утверждений). Числа несравнимы.
4. **Диагноз «низкая relevancy»:** QASkills — промпт; Atlan — не тот контент. Обе версии возможны; разводить по context precision.
5. По формулам faithfulness / precision / recall противоречий нет.

## 6. Пятое измерение: достоверность контекста (из источника №3)

Все четыре метрики **предполагают, что индекс заслуживает доверия**. Ответ, верный устаревшему контексту, получит зелёные метрики и будет неверен в бизнес-смысле.

**Четыре вопроса к каждому фрагменту индекса:**
- Свежесть (freshness) — когда пересматривался?
- Владение (ownership) — есть ли ответственный? (нет владельца → опережающий индикатор устаревания)
- Происхождение (lineage integrity) — прослеживается ли до канонического источника?
- Каноническое согласование (canonical alignment) — совпадает ли с определением «у финансов/команды данных»?

**Три практики:**
1. Доверенные дашборды как ground truth («агент не согласен с дашбордом → прав дашборд»; несогласие = диагностический сигнал: контента нет / определения разошлись / контент устарел).
2. Каждая правка пользователя — сигнал оценки → маршрутизировать в индекс.
3. Непрерывный мониторинг: возраст определений, покрытие владельцами, полнота lineage, актуальность схем.

*Примечание: статья вендорская (Atlan), но практики применимы без их продукта — это governance над корпусом документов.*

## 8. Протокол эксперимента 512 → 256 (практика дня)

**Гипотеза:** recall ↑ (мельче чанки → точнее попадание), precision ↓ (больше чанков в top-k → шум), возможна просадка faithfulness через шум в генерации.

**Чтобы дельта была интерпретируемой:**
1. Зафиксировать модель-судью и эмбеддинги (те же между прогонами).
2. Тот же датасет, те же метрики: faithfulness + answer relevancy везде; context recall + factual correctness только где есть golden answers.
3. 2–3 прогона на каждую конфигурацию → смотреть разброс, не одно число.
4. Записать обе конфигурации в JSONL (метрики + commit/конфиг + timestamp).
5. Интерпретировать дельту по таблице 2×2 (раздел 3).

## 9. Шпаргалка «метрика → компонент → ручка»

| Симптом | Компонент | Ручка |
|---|---|---|
| Низкий faithfulness | Генератор | Промпт (запрет додумывания), модель |
| Низкая relevancy | Генератор или ретрив | Промпт; проверить precision |
| Низкий precision | Ретрив (ранжирование) | Реранкер |
| Низкий recall | Ретрив (покрытие) | top-k, размер чанка, эмбеддинги |
| Precision и recall низкие | Ретрив (базово) | Эмбеддинги, индексация |
| Высокий faithfulness + низкая correctness | Корпус/ретрив | Индекс, свежесть контента |
| Всё зелёное, но ответы «не те» | Индекс | Пятое измерение: свежесть, владение, lineage |
