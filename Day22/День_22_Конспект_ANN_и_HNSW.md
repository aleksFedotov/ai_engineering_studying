## 1. Постановка проблемы

- Задача: найти k ближайших соседей (k-NN / k-Nearest Neighbors) к вектору запроса в базе эмбеддингов.
- **Точный поиск (brute force)**: посчитать расстояние до **каждого** вектора — O(n) на запрос. Не масштабируется на миллионах векторов.
- **Приближённый поиск ближайших соседей (ANN / approximate nearest neighbors)**: жертвуем небольшой долей точности ради большого выигрыша в скорости.
- Метрика качества ANN — **полнота (recall)**: доля истинных k соседей, которую алгоритм нашёл. Recall = 0.98 → в среднем 9.8 из 10 истинных соседей. Именно recall < 100% — главная цена за скорость.

## 2. HNSW = две идеи

**HNSW (Hierarchical Navigable Small World)** — иерархический навигационный маленький мир. Авторы: Ю. А. Малков и Д. А. Яшунин, статья 2016 года. Графовый ANN-алгоритм, лидер по балансу скорость/точность/масштабируемость.

### Идея 1. Список с пропусками (skip list)
- Связный список: доступ O(n). Skip list: + экспресс-уровни → O(log n).
- Цена: память O(n log n) вместо O(n), оверхед на вставки/удаления.
- Вставка вероятностная: элемент со слоя попадает на слой выше с вероятностью p → плотность уровней экспоненциально убывает вверх.
- Требует **отсортированных** данных (иначе «скип» может отбросить искомое).

### Идея 2. Навигационный маленький мир (NSW)
- Граф: у узла связи трёх дальностей — короткие, средние, дальние. Аналогия — «шесть рукопожатий».
- Поиск — **жадный (greedy search)**: из точки входа (entry point) переходим к соседу, ближайшему к запросу, пока не застрянем в локальном минимуме.
- Проблема: чистый NSW деградирует на больших данных. Лечение «в лоб» (больше связей на узел) раздувает сеть; предел — полносвязный граф = линейный поиск.

### Сборка: HNSW
- Слои NSW-графов вместо уровней списка. Нижний слой (Layer 0) — все точки; выше — случайные подмножества, всё разреженнее.
- Поиск **сверху вниз**: на каждом слое жадным поиском находим локальный минимум → он становится entry point для слоя ниже.
- Верхние слои = «шоссе» (быстро пересечь пространство), нижние = «местные улицы» (точная навигация). Итог: ~O(log n) вместо O(n).
- Вставка: выбираем слой по формуле, спускаемся, на своём слое и ниже связываемся **двунаправленными** рёбрами с ближайшими (до M штук). Фазы обучения нет — индекс строится инкрементально.

## 3. Формула выбора слоя

```
layer = floor(-ln(rand(0, 1)) · m_L)
```

- `-ln(rand)` — экспоненциально убывающее распределение: чем выше слой, тем меньше узлов.
- **m_L (level multiplier)** — крутизна убывания:
  - **↑ m_L → слои плотнее** (узлы чаще попадают высоко);
  - **↓ m_L → слои разреженнее**.
- Стандартный выбор: `m_L = 1/ln(M)` → каждый слой в среднем в **M раз** разреженнее нижнего.
- Минимальное расстояние между узлами слоя не гарантируется — граф теоретически может построиться неудачно, но вероятность пренебрежимо мала.

## 4. Три параметра (+ бонус)

| Параметр | Что делает | ↑ параметр | Цена |
|---|---|---|---|
| **M** | максимум связей на узел | качественнее, связнее граф, выше потолок recall | память + время построения |
| **efConstruction** | тщательность поиска соседей при вставке (размер списка кандидатов при построении) | качественнее граф | время индексации |
| **efSearch** | размер списка кандидатов при поиске | выше recall | **медленнее запрос** (↑ latency) |
| **m_L** (бонус) | крутизна разрежения слоёв | плотнее верхние слои | больше память наверху |

Ключевые факты:
- M и efConstruction — параметры **времени построения**: меняем → перестраиваем индекс.
- efSearch — параметр **времени запроса**: крутится на лету, **без переиндексации**. Это главная «ручка» после сборки.
- **↑ efSearch → ↑ recall, ↓ скорость запроса** (не наоборот!).

**Порядок настройки (из источника №1):** дефолты → замер recall и latency на валидации → recall низкий? поднять efSearch → упёрся в потолок? переиндексация с ↑ efConstruction → всё ещё мало? ↑ M.

## 5. Как это выглядит в коде (по Zilliz)

- `_search_layer(graph, entry, query, ef)` — жадный поиск по одному слою: куча кандидатов `candid` + список `nns` лучших ef. Стоп: кандидаты кончились ИЛИ ближайший кандидат хуже худшего найденного.
- `search`: на верхних слоях `_search_layer` с **ef=1** (одна точка-прицел для спуска), только на нижнем — полный ef. → «шоссе» проходится за копейки, бюджет efSearch тратится только внизу.
- `insert`: выбор слоя по формуле → спуск → на слое и ниже двунаправленные связи с ef-соседями.
- **Pruning (отсечение)** — в полной реализации при вставке списки соседей обрезаются до M; без него старые узлы «обрастают» связями. (В учебном коде Zilliz опущен.)

## 6. Сравнение с другими ANN-подходами

| Подход | Идея | Когда хорош | Слабость |
|---|---|---|---|
| **KD-Trees** | делят пространство пополам по осям | низкая размерность | деградирует с ростом размерности |
| **LSH** (локально-чувствительное хеширование) | похожие векторы в одни «корзины» | очень высокая размерность, разреженные векторы | страдает recall |
| **IVF** (инвертированный файловый индекс) | кластеры вокруг центроидов, ищем в нескольких | очень большие базы, скорость | recall ниже среднего, нужна предварительная кластеризация |
| **HNSW** | слоистый граф «маленьких миров» | высокий recall + скорость, инкрементальные обновления | память, стоимость построения, шардирование |

## 7. Цена HNSW (контрольная точка дня)

HNSW отвечает по миллиону векторов за миллисекунды (~O(log n)), жертвуя:

1. **Гарантией точного ответа** — recall < 100% (жадный поиск может застрять в локальном минимуме). Главная цена!
2. **Памятью** — граф связей + векторы, растёт с M (O(n log n) по слоям).
3. **Стоимостью построения** — жадный поиск при каждой вставке (лечится параллельной сборкой).
4. **Простотой масштабирования** — лучше всего работает как монолитный индекс в RAM; шардирование добавляет сложности и памяти.

**Три причины, почему поиск приближённый:**
1. **Жадность** — локальный минимум ≠ глобальный.
2. **Вероятность** — случайная разметка слоёв, граф может построиться неудачно.
3. **Отсечение кандидатов** — ef ограничен, нужный узел может не попасть в список.

## 8. Brute force vs ANN: граница применимости

Brute force выбираем, когда:
- датасет малый (грубый ориентир — до ~1 млн векторов);
- память важнее скорости (граф не бесплатный);
- нужна **гарантия точного ответа** (аудит, эталонные замеры, измерение recall самого ANN-индекса).

ANN (HNSW) — когда:
- миллионы+ векторов и/или высокая нагрузка (запросов/сек);
- скорость и масштабируемость важнее идеальной точности.

## 9. Best practices (источник №1)

1. Оптимизация памяти: ↓ M, сжатие векторов (FAISS), снижение размерности (случайная проекция).
2. Тюнинг параметров под свой баланс recall/скорость (порядок — см. §4).
3. Параллельная многопоточная сборка индекса.
4. Инкрементальные вставки/удаления вместо полной переиндексации.
5. Измерять recall и latency на валидационном наборе, а не «на глаз».

## 10. Замечания к источникам

- Источник №1 (Redis): в разделе trade-offs путаница — «lowering efSearch → faster indexing» неверно (efSearch влияет на запрос, не на индексацию). Бенчмарки «Redis быстрее всех» — маркетинг вендора.
- Источник №2 (Zilliz): учебный код упрощён (нет pruning, шероховатости в сигнатурах). Для практики — `hnswlib`, `usearch`, `faiss`.
- Нумерация слоёв в библиотеках: **Layer 0 — нижний полный граф** (как у Zilliz и в оригинальной статье).
- Названия параметров в библиотеках: M → `connectivity` (usearch); efConstruction → `expansion_add`; efSearch → `expansion_search` / `ef`.
