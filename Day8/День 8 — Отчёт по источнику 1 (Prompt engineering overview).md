## 1. Что это за страница и какую роль она играет

Страница «Prompt engineering overview» — это **входная точка и карта всей системы промптинга Anthropic**. Она намеренно короткая: её задача не научить техникам, а задать **методологию** — в каком порядке и когда вообще стоит заниматься промпт-инжинирингом, и где лежит «живой справочник» техник.

Главная мысль страницы: **промпт-инжиниринг — это инженерный цикл, а не подбор «волшебных слов»**. Прежде чем крутить формулировки, нужно сделать домашнюю работу: критерии успеха, способ измерения, черновик промпта.[^1^]

## 2. «Before prompt engineering» — три предпосылки

Руководство предполагает, что у вас уже есть:[^1^]

1. **Чёткое определение критериев успеха** для вашей задачи.
2. **Способ эмпирически проверять** промпт на соответствие этим критериям (evals).
3. **Первый черновик промпта**, который вы хотите улучшить.

Если чего-то из этого нет — сначала займитесь этим, а не техниками. Это ключевой дисциплинирующий принцип: улучшение промпта без измерения — это гадание.

### 2.1. Критерии успеха (из связанной страницы «Define success criteria and build evaluations»)

Хорошие критерии успеха — это:[^2^]

| Принцип | Что значит | Плохой пример | Хороший пример |
|---|---|---|---|
| **Specific** (конкретный) | Точно определите, чего хотите | «хорошее качество ответов» | «точная классификация тональности отзыва» |
| **Measurable** (измеримый) | Количественная метрика или строгая качественная шкала | «ответы безопасные» | «менее 0,1% ответов из 10 000 прогонов помечаются фильтром как токсичные» |
| **Achievable** (достижимый) | Цели опираются на бенчмарки, прошлые эксперименты, экспертизу | «100% точность всегда» | цель на уровне возможностей фронтирных моделей |
| **Relevant** (релевантный) | Критерий привязан к цели приложения и нуждам пользователей | требовать идеальных цитат от casual-чат-бота | точность цитирования — критична для медицинского приложения |

Важная деталь: даже «размытые» темы вроде этики и безопасности **можно квантифицировать** — пример с «0,1% из 10 000 триалов» прямо из документации.[^2^] Большинству реальных задач нужна **многомерная оценка** сразу по нескольким критериям (точность + тон + формат + латентность и т.д.).

### 2.2. Evals — эмпирическая проверка

Цикл промпт-инжиниринга по Anthropic выглядит так:[^2^]

```
Разработать тест-кейсы → Написать черновой промпт → Прогнать промпт по кейсам
      ↑                                                    ↓
      └────────────── Доработать промпт ←──────────────────┘
                           ↓
        Проверить на отложенных (held-out) evals → Отправить в прод
```

Три принципа дизайна evals:[^2^]

1. **Будьте специфичны к задаче** — evals должны отражать реальное распределение задач. Не забывайте про краевые случаи (edge cases)!
2. **Автоматизируйте, где можно** — формулируйте вопросы так, чтобы оценка была автоматической (multiple choice, совпадение строк, проверка кодом, оценка другой LLM).
3. **Объём важнее качества** — много вопросов с чуть менее точной автоматической оценкой лучше, чем мало вопросов с идеальной ручной разметкой.

### 2.3. Три способа грейдинга (от лучшего к запасному)

По скорости, надёжности и масштабируемости:[^2^]

1. **Кодом** — самый быстрый, надёжный и масштабируемый, но негибкий:
   - точное совпадение: `output == golden_answer`
   - совпадение подстроки: `key_phrase in output`
2. **Человеком** — самый качественный и гибкий, но медленный и дорогой. Избегайте, если возможно.
3. **LLM-судьёй** — быстро, гибко, масштабируемо, подходит для сложных суждений. Сначала проверьте надёжность судьи, потом масштабируйте.

Советы для LLM-грейдинга:[^2^]
- **Детальные рубрики**: «Ответ должен упоминать "Acme Inc." в первом предложении. Если нет — автоматически "incorrect"».
- **Конкретный формат вердикта**: пусть судья выводит только `correct`/`incorrect` или оценку по шкале 1–5.
- **Сначала рассуждение, потом оценка**: попросите LLM-судью рассудить, а затем выдать вердикт (рассуждение отбрасывается) — это повышает качество оценки на сложных задачах.

### 2.4. Нет черновика промпта? Метапромпт

Если у вас нет первого черновика, Anthropic предлагает сгенерировать его **метапромптом** из Claude Cookbook:[^1^] это шаблон, где вы описываете задачу модели, а Claude сам генерирует структурированный промпт-заготовку (с инструкциями, переменными и примерами), которую вы затем дорабатываете. То есть стартовую точку можно получить от самой модели, а не писать с нуля.[^3^]

## 3. «When to prompt engineer» — когда промптинг вообще уместен

Критически важный раздел, который часто пропускают:[^1^]

> **Не всякий провал на evals решается промпт-инжинирингом.**

Гайд фокусируется только на тех критериях успеха, которые **контролируются через промпт**. Контрпример из документации: **латентность и стоимость** часто проще улучшить, выбрав другую модель (например, более лёгкую), чем переписывая промпт.[^1^]

Практический вывод — матрица решений:

| Проблема | Инструмент решения |
|---|---|
| Неточные ответы, неверный формат, плохой тон | Промпт-инжиниринг (техники) |
| Медленно / дорого | Выбор другой модели, снижение effort, сокращение контекста |
| Модель не знает фактов | RAG / инструменты / данные в контексте, а не промпт |
| Нестабильность на сложных многошаговых задачах | Thinking, chaining, агентная архитектура |

## 6. Примеры для усвоения

### Пример 1: постановка критериев успеха для рабочей задачи

Допустим, задача — «промпт, который из письма клиента извлекает тему обращения».

**Плохо (не по методологии):** «хочу, чтобы классифицировал хорошо».

**Хорошо (по четырём принципам):**
- *Specific:* классификация обращения в одну из 8 категорий (возврат, оплата, доставка, …).
- *Measurable:* точность ≥ 95% на тесте из 200 писем; формат ответа — строго `{"category": "...", "confidence": 0-1}`.
- *Achievable:* базовый уровень — 88% у чернового промпта; цель 95% реалистична.
- *Relevant:* точность важнее скорости, т.к. от категории зависит маршрутизация тикета.

### Пример 2: мини-eval с кодовым грейдингом

```python
test_cases = [
    {"input": "Деньги списали дважды!", "golden": "оплата"},
    {"input": "Посылка неделю висит в сортировке", "golden": "доставка"},
    # ... 200 кейсов, включая edge cases:
    {"input": "", "golden": "неопределено"},            # пустой ввод
    {"input": "верните деньги и где мой заказ?!", "golden": "неоднозначно"},  # две темы
]

passed = sum(classify(c["input"]) == c["golden"] for c in test_cases)
print(f"Accuracy: {passed / len(test_cases):.1%}")
```

Обратите внимание на edge cases — документация специально напоминает: «Don't forget edge cases!».[^2^]

### Пример 3: рубрика для LLM-судьи

```
Ты — судья качества саммари. Оцени ответ ассистента по критериям:
1. Саммари содержит все ключевые цифры из исходного текста.
2. Длина саммари не превышает 3 предложений.

Сначала кратко рассуди по каждому критерию, затем выведи вердикт
ОДНИМ словом: correct или incorrect.

<исходный_текст>{{document}}</исходный_текст>
<ответ_ассистента>{{summary}}</ответ_ассистента>
```

Вердикт парсится кодом — это масштабируемо на тысячи прогонов.

### Пример 4: полный цикл «тест → рефайн» на практике

1. Пишете черновик промпта-классификатора → accuracy 88%.
2. Смотрите на 24 ошибки: 15 из них — письма с двумя темами.
3. Дорабатываете промпт: добавляете правило «если тем несколько, выбирай главную по принципу X» + 2 примера таких писем (multishot).
4. Прогоняете снова → 94%.
5. Финальная проверка на **отложенном** наборе (held-out), который не использовался при доработке → 93,5%. Нет переобучения на тест — можно в прод.

Именно этот цикл, а не «попробовал — не понравилось — переписал», Anthropic называет промпт-инжинирингом.[^2^]
