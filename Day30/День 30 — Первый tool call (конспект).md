# 1. Базовая модель tool calling

## Что такое вызов инструмента

**Вызов инструмента (tool call)** или **вызов функции (function call)** — это структурированный ответ модели, в котором она сообщает приложению:

- какую функцию нужно выполнить;
- какие аргументы ей передать;
- каким идентификатором связать результат с вызовом.

Обычный текстовый ответ предназначен пользователю. Function call предназначен приложению.

## Общий цикл

```text
Пользователь задаёт вопрос
        ↓
Модель получает вопрос и описание инструментов
        ↓
Модель возвращает вызов инструмента
        ↓
Приложение выполняет функцию
        ↓
Приложение возвращает результат модели
        ↓
Модель формирует финальный ответ
```

Важно: обычно происходит два обращения к модели. Первое нужно, чтобы модель выбрала инструмент и аргументы. Второе — чтобы она использовала полученный результат в ответе.

## Разделение ответственности

- Приложение описывает доступные инструменты, их имена, параметры и назначение.
- Модель выбирает инструмент и формирует аргументы.
- Код выполняется вне модели.
- Результат возвращается модели через специальный формат.

# 2. Источник №1 — OpenAI Playground

## Назначение

OpenAI Playground — интерактивная среда для проверки промптов, схем функций и поведения модели без написания приложения.

Для практики с Responses API важны:

- панель инструментов;
- редактор схемы функции;
- область диалога;
- отображение вызова функции;
- ручной ввод результата функции;
- итоговый ответ модели.

## Схема функции

Основные поля определения функции:

| Поле | Назначение |
|---|---|
| `type` | Тип инструмента; для функции — `function` |
| `name` | Имя функции, которое будет искать код |
| `description` | Описание, когда и зачем использовать инструмент |
| `parameters` | JSON-схема входных аргументов |
| `strict` | Включение строгого соответствия схеме |

Внутри `parameters` используются:

- `type` — тип корневого значения, обычно `object`;
- `properties` — описание допустимых аргументов;
- `required` — массив обязательных имён аргументов;
- `additionalProperties` — разрешены ли лишние поля.

Важно:

- `required` — это массив, а не `true` или `false`;
- `additionalProperties: false` запрещает лишние поля;
- `additionalProperties: true` или отсутствие поля обычно разрешает дополнительные свойства.

## Строгий режим

**Строгий режим (strict mode)** требует, чтобы аргументы вызова соответствовали JSON-схеме.

Для простой функции `get_weather(city)` важны:

- `city` указан в `properties`;
- `city` указан в `required`;
- `additionalProperties` установлен в `false`;
- `strict` установлен в `true`.

## Что возвращает OpenAI

В Responses API вызов функции приходит как элемент `output` с типом `function_call`.

Ключевые поля:

| Поле | Назначение |
|---|---|
| `type` | Тип элемента: `function_call` |
| `id` | Идентификатор элемента в ответе |
| `call_id` | Идентификатор конкретного вызова |
| `name` | Имя выбранной функции |
| `arguments` | Аргументы как JSON-закодированная строка |

Особенность OpenAI: `arguments` — это строка, содержащая JSON. В Python её обычно преобразуют через `json.loads()`.

## Как вернуть результат

Результат возвращается элементом `function_call_output`.

Ключевые поля:

| Поле | Назначение |
|---|---|
| `type` | Тип элемента: `function_call_output` |
| `call_id` | Идентификатор вызова, к которому относится результат |
| `output` | Результат функции, обычно строка с JSON внутри |

Связь вызова и результата происходит через `call_id`.

## Выбор инструмента

**Выбор инструмента (tool choice)** определяет, как модель решает, вызывать ли функцию:

- `auto` — модель сама решает;
- `required` — модель должна вызвать хотя бы один инструмент;
- конкретная функция — модель должна вызвать именно её;
- `none` — вызовы запрещены.

Для проверки естественного поведения лучше использовать `auto`. Принудительный вызов полезен для тестирования схемы.

## Параллельные вызовы

**Параллельный вызов функций (parallel function calling)** — это ситуация, когда модель формирует несколько вызовов за один ход.

Это не означает, что модель сама выполняет функции параллельно. Параллельное или последовательное исполнение организует приложение.

## Стоимость схем

Описания функций занимают место в **контекстном окне (context window)** и учитываются как **входные токены (input tokens)**. Поэтому не следует без необходимости добавлять много инструментов и слишком длинные описания.

# 3. Источник №2 — Anthropic Console / Playground

## Назначение

Anthropic Console Playground — среда для тестирования Messages API, просмотра SDK-запроса, сырого API-ответа и блоков вызова инструментов.

## Определение пользовательского инструмента

Основные поля:

| Поле | Назначение |
|---|---|
| `name` | Имя инструмента |
| `description` | Подробное описание назначения и поведения |
| `input_schema` | JSON-схема входных аргументов |
| `input_examples` | Необязательные примеры корректных входных данных |
| `strict` | Требование строгого соответствия входных данных схеме |

Главное отличие от OpenAI: схема аргументов называется `input_schema`, а не `parameters`.

## Блок tool_use

Если Claude решает вызвать клиентский инструмент, ответ содержит **блок вызова инструмента (tool_use block)** и обычно `stop_reason: "tool_use"`.

Ключевые поля `tool_use`:

| Поле | Назначение |
|---|---|
| `type` | Тип блока: `tool_use` |
| `id` | Идентификатор конкретного вызова |
| `name` | Имя выбранного инструмента |
| `input` | Аргументы как обычный JSON-объект |

Особенность Anthropic: `input` уже является объектом, а не JSON-закодированной строкой.

## Причина остановки

**Причина остановки (stop reason)** показывает, почему модель завершила текущий ответ.

Важные значения:

- `tool_use` — модель ждёт выполнения клиентского инструмента;
- `end_turn` — модель завершила ответ;
- `max_tokens` — достигнут лимит токенов;
- `stop_sequence` — встречена стоп-последовательность;
- `refusal` — модель отказалась выполнять запрос;
- `pause_turn` — серверный цикл приостановлен и должен быть продолжен.

## Блок tool_result

Результат клиентского инструмента возвращается блоком **результата инструмента (tool_result block)** внутри нового сообщения с ролью `user`.

Ключевые поля:

| Поле | Назначение |
|---|---|
| `type` | Тип блока: `tool_result` |
| `tool_use_id` | Идентификатор вызова, к которому относится результат |
| `content` | Результат выполнения |
| `is_error` | Необязательный признак ошибки |

`tool_use_id` должен совпадать с `id` из блока `tool_use`.

То, что `tool_result` находится в сообщении с ролью `user`, не означает, что результат написал человек. Роль `user` здесь является контейнером следующего входа модели, а тип `tool_result` показывает, что внутри находится результат инструмента.

## Полная история диалога

После вызова клиентского инструмента в следующий запрос нужно включить:

1. исходное сообщение пользователя;
2. ответ ассистента с блоком `tool_use`;
3. новое сообщение с блоком `tool_result`.

Нельзя отправлять изолированный `tool_result` без предыдущего `tool_use`: идентификатор результата потеряет контекст.

## tool_choice у Anthropic

Режимы **выбора инструмента (tool choice)**:

| Режим | Поведение |
|---|---|
| `auto` | Claude сам решает, вызывать ли инструмент |
| `any` | Claude должен вызвать хотя бы один инструмент |
| `tool` | Claude должен вызвать конкретный инструмент |
| `none` | Вызов инструментов запрещён |

Параллельные вызовы можно отключить через `disable_parallel_tool_use` внутри `tool_choice`.

## Параллельные вызовы Anthropic

Если Claude возвращает несколько `tool_use`, нужно вернуть по одному `tool_result` на каждый вызов. Все результаты должны находиться в следующем сообщении с ролью `user` и связываться с вызовами через `tool_use_id`.

# 4. Сравнение OpenAI и Anthropic

| Этап | OpenAI Responses API | Anthropic Messages API |
|---|---|---|
| Определение функции | `type: function` + `parameters` | `name` + `description` + `input_schema` |
| Вызов | `function_call` | `tool_use` |
| Идентификатор вызова | `call_id` | `id`, затем `tool_use_id` |
| Аргументы | `arguments` — JSON-закодированная строка | `input` — JSON-объект |
| Результат | `function_call_output` | `tool_result` |
| Поле результата | `output` | `content` |
| Сигнал вызова | Найти элемент `function_call` в `output` | `stop_reason: tool_use` и блоки `tool_use` |
| Обязательный вызов любого инструмента | `tool_choice: required` | `tool_choice: {"type": "any"}` |
| Вызов конкретного инструмента | `{"type": "function", "name": "..."}` | `{"type": "tool", "name": "..."}` |
| Отключение параллельных вызовов | `parallel_tool_calls: false` | `disable_parallel_tool_use: true` |
| Возврат результата | Элемент добавляется в `input` | Блок добавляется в сообщение с ролью `user` |

Главные практические различия:

1. У OpenAI аргументы нужно дополнительно парсить из строки.
2. У Anthropic аргументы уже представлены объектом.
3. У OpenAI результат связан через `call_id`.
4. У Anthropic результат связан через `tool_use_id`.
5. У Anthropic управляющим сигналом цикла обычно является `stop_reason`.

# 5. Источник №3 — How tool use works

## Tool-use contract

**Контракт использования инструментов (tool-use contract)** — это соглашение между приложением и моделью:

- приложение описывает доступные операции;
- модель выбирает операцию и аргументы;
- приложение или Anthropic выполняет код;
- результат возвращается в диалог.

Фраза «модель ничего не выполняет сама» означает, что код не запускается внутри модели. Выполнение всегда происходит во внешней среде.

## Три категории инструментов

| Категория | Кто пишет схему | Кто выполняет код | Кто возвращает результат |
|---|---|---|---|
| Пользовательский клиентский инструмент (user-defined client tool) | Разработчик | Приложение | Приложение отправляет `tool_result` |
| Клиентский инструмент со схемой Anthropic (Anthropic-schema client tool) | Anthropic | Приложение | Приложение отправляет `tool_result` |
| Серверный инструмент (server-executed tool) | Anthropic | Инфраструктура Anthropic | Anthropic включает результат в ответ |

## Пользовательский клиентский инструмент

Пример — `get_weather(city)`.

- Схему пишет разработчик.
- Функцию реализует разработчик.
- Результат возвращает приложение через `tool_result`.

## Клиентский инструмент со схемой Anthropic

Примеры — `bash`, `text_editor`, `memory`, `computer`, `browser`.

- Anthropic определяет интерфейс и схему.
- Модель обучена пользоваться этой схемой.
- Приложение выполняет операцию.

Название «Anthropic» здесь означает авторство схемы, а не серверное выполнение.

## Серверный инструмент

Примеры — `web_search`, `web_fetch`, `code_execution`, `tool_search`.

- Anthropic определяет схему.
- Anthropic выполняет операцию.
- Приложение не пишет обработчик и обычно не создаёт `tool_result`.

Поэтому `web_search` и `get_weather` принципиально различаются: поиск выполняется инфраструктурой Anthropic, а пользовательская функция — кодом приложения.

## Агентный цикл

**Агентный цикл (agentic loop)** для клиентских инструментов:

1. Отправить инструменты и сообщение пользователя.
2. Получить `stop_reason: tool_use`.
3. Выполнить каждый `tool_use`.
4. Добавить ответ ассистента и `tool_result` в историю.
5. Повторять, пока модель продолжает запрашивать инструменты.

Цикл завершится при другой причине остановки.

## Серверный цикл

**Серверный цикл (server-side loop)** выполняется инфраструктурой Anthropic. Например, один вопрос может привести к нескольким внутренним поискам, после чего приложение получит готовый ответ.

## pause_turn

`pause_turn` означает, что серверный цикл достиг лимита итераций, но работа ещё не завершена.

Правильное действие — отправить диалог обратно, включая приостановленный ответ ассистента, чтобы Anthropic продолжил с того же места. Это не ошибка и не повод реализовывать серверный инструмент самостоятельно.

## Смешанная группа вызовов

Если модель в одной параллельной группе вызывает клиентский и серверный инструменты, управление может вернуться приложению до выполнения серверного вызова.

Порядок:

1. Приложение выполняет клиентский `tool_use`.
2. Приложение возвращает `tool_result`.
3. Anthropic выполняет серверный вызов.
4. Модель продолжает работу.

Наличие `server_tool_use` не всегда означает, что серверный инструмент уже выполнен.

# 6. Когда использовать инструменты

Инструменты нужны, если задача требует:

- актуальных или внешних данных;
- действия с побочным эффектом;
- обращения к базе данных или API;
- структурированного результата;
- работы с файлами, браузером или операционной системой.

Примеры, где инструмент уместен:

- текущая погода;
- цена акции;
- отправка письма;
- создание задачи;
- чтение внутренней базы данных;
- изменение файла.

Инструменты обычно не нужны, если:

- модель может ответить из общих знаний;
- задача является переводом, суммаризацией или объяснением;
- нет побочных эффектов;
- не требуются внешние данные.

Полезный критерий: если приходится регулярным выражением извлекать решение модели из свободного текста, вероятно, это решение должно было быть вызовом инструмента.

# 7. SDK, фреймворки и инструменты со схемой Anthropic

## Messages API

При ручной работе с Messages API Anthropic предоставляет схему, но исполнитель клиентского инструмента обычно реализуется приложением.

Для множества инструментов удобно использовать:

- реестр обработчиков (handler registry);
- диспетчер (dispatcher);
- отдельный слой проверки разрешений (permission layer);
- единый формат результата и ошибки.

## Tool Runner

Tool Runner в обычном SDK помогает управлять циклом и вызывать зарегистрированные Python-функции. Он автоматизирует протокольную часть, но не придумывает бизнес-логику функции.

## Claude Agent SDK

Claude Agent SDK — более высокий уровень. Для встроенных инструментов вроде `Read`, `Write`, `Edit` и `Bash` реализация уже существует в инфраструктуре Claude Code, а разработчик настраивает:

- рабочую директорию;
- разрешённые и запрещённые инструменты;
- режим разрешений;
- перехватчики (hooks);
- проверки безопасности.

Встроенные инструменты Agent SDK и Anthropic-schema client tools функционально пересекаются, но это не всегда одна и та же поверхность интеграции.

# 8. Важные исправления после самопроверки

## 1. `required`

`required` — массив обязательных параметров:

- правильно: `required: ["city"]`;
- неправильно: `required: true`.

## 2. `additionalProperties`

- `additionalProperties: false` запрещает лишние поля;
- `additionalProperties: true` разрешает лишние поля.

## 3. `arguments` и `input`

- OpenAI `arguments` — строка с JSON;
- Anthropic `input` — объект.

## 4. Идентификаторы

У OpenAI:

- `id` — идентификатор элемента ответа;
- `call_id` — идентификатор вызова для возврата результата.

У Anthropic:

- `id` в `tool_use` — идентификатор вызова;
- `tool_use_id` в `tool_result` — ссылка на этот вызов.

## 5. История диалога

Результат инструмента нельзя отправлять изолированно. Нужно сохранять цепочку:

```text
исходный запрос → ответ ассистента с вызовом → сообщение с результатом
```

## 6. Синтаксис JSON

- между парами ключ–значение нужны запятые;
- после последнего элемента объекта или массива запятой быть не должно;
- JSON внутри строки подчиняется тем же правилам.

# 10. Быстрая шпаргалка

## OpenAI

```text
Схема:      type=function, parameters
Вызов:      function_call
Аргументы:  arguments — строка JSON
Идентификатор: call_id
Результат:  function_call_output
Поле:       output
```

## Anthropic

```text
Схема:      input_schema
Вызов:      tool_use
Аргументы:  input — объект
Идентификатор: tool_use.id
Результат:  tool_result
Связь:      tool_result.tool_use_id = tool_use.id
Сигнал:     stop_reason=tool_use
```

## Кто выполняет код

```text
Пользовательская функция     → приложение
Anthropic-schema client tool → приложение
Server tool                  → инфраструктура Anthropic
```

# 12. Главная мысль дня

Tool calling — это не «модель запускает функцию», а протокол обмена:

> Модель формирует структурированную заявку. Внешняя среда выполняет операцию. Результат возвращается модели. Только после этого модель может дать пользователю ответ, основанный на реальных данных.
