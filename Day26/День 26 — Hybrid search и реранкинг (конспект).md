## Теория

### Три класса моделей (ист. №1)
- **SentenceTransformer (би-энкодер / bi-encoder)** — кодирует запрос и документ **по отдельности** → документы можно заранее проиндексировать. Быстро, масштабируется на миллионы.
- **SparseEncoder** — обучаемый разреженный эмбеддинг (SPLADE): вектор размером со словарь (30k+), почти все нули, ненулевые = веса терминов. Хранится в инвертированном индексе (inverted index). Ловит точные термины + делает term expansion (учит синонимы).
- **CrossEncoder (кросс-энкодер)** — читает пару «запрос + один кандидат» **вместе** (joint attention) → точнее, но медленно: только по шортлисту (50–100).

### encode_query / encode_document
Современные retrieval-модели обучены с разными инструктивными промптами для запроса и документа (у E5: `"query: "` / `"passage: "`). Пропуск промпта — **тихая** ошибка: код работает, качество ниже.

### Паттерн retrieve-then-rerank
Би-энкодер кидает широкую быструю сеть (топ-50–100), кросс-энкодер тратит бюджет точности на выживших. Кросс-энкодер по всему корпусу не масштабируется (скорит по одной паре).

### BM25 (ист. №2)
Стоит на TF-IDF + два улучшения:
1. **Насыщение частоты термина** (term frequency saturation) — 10 повторов не в 10 раз важнее одного;
2. **Нормализация по длине документа** — длинный документ не получает преимущество от количества слов.

Редкие термины (коды, аббревиатуры, имена функций) получают огромный IDF → BM25 «выстреливает» их наверх. В этом его суперсила в гибриде.

### RRF — Reciprocal Rank Fusion (ист. №1)
Скоры dense и BM25 несопоставимы (косинус 0.8 vs вес 25.4) → складывать нельзя. RRF комбинирует **позиции (ранги)**, а не скоры:

```
score_RRF(d) = Σ по ретриверам  1 / (k + rank)
```

- k = 60 — из оригинальной статьи, гасит разрыв между соседними рангами (при k=0 первое место вдвое важнее второго, при k=60 — почти не отличается). Крутить редко имеет смысл.
- Документ, высокий в **обоих** списках, всплывает; одиночное лидерство **наказывается** (см. наблюдение из практики ниже).
- Альтернатива: DBSF (Distribution-Based Score Fusion) — нормализует скоры по статистике распределения (μ ± 3σ), «слушает уверенность», но чувствительна к выбросам. Дефолт — RRF.

### Contextual Retrieval (ист. №2, тема на вырост)
- Проблема: чанкинг **разрушает контекст** — чанк «выручка выросла на 3%» не знает ни компании, ни квартала.
- Решение: LLM (по промпту «situate this chunk within the document») пишет 50–100 токенов контекста, который **prepend**-ится к чанку **до** эмбеддинга и **до** BM25-индекса.
- Результаты Anthropic (метрика 1 − recall@20, доля промахов): 5.7% → 3.7% (только контекстные эмбеддинги, −35%) → 2.9% (+ контекстный BM25, **−49%**) → 1.9% (+ реранкинг, **−67%**). Эффекты складываются.
- Общее саммари документа НЕ работает — нужен кусочно-специфичный контекст. Цифры — блог вендора: порядок эффекта, не гарантия.
- Бонус: если база знаний < ~200k токенов, RAG может вообще не понадобиться — всё в промпт + prompt caching.

### Qdrant / инфраструктура (ист. №3)
- **Named vectors**: одна точка хранит несколько векторов с именами (`dense`, `sparse`); у sparse нет `size` — хранятся только ненулевые пары `{индекс: вес}`.
- Серверное слияние: `FusionQuery(Fusion.RRF)` поверх двух `prefetch`. Ручное слияние всё ещё нужно, когда ретриверы в разных движках или нужна кастомная логика.
- Фильтры по payload применяются **во время** поиска (pre-filtering в HNSW), не после: пост-фильтрация топ-10 может оставить 1 результат.

### Типичные ошибки (ист. №1)
1. Смешение моделей между индексацией и запросами (эмбеддинги в несовместимых пространствах). Сменил модель → переэмбедди корпус; версионируй индекс именем модели.
2. Пропуск encode_query/encode_document — тихая потеря качества.
3. Тихое усечение (silent truncation): чанки длиннее max_seq_length обрезаются без предупреждения (у MiniLM всего 256 токенов!). У кросс-энкодера лимит общий на запрос+документ.
4. Выбор модели по лидерборду MTEB вместо своего eval.
5. Переэмбеддинг корпуса на каждый запрос — кэшируй.
6. Кросс-энкодер по всему корпусу — только шортлист.
7. Дообучение без hard negatives и без eval.
8. Игнорирование лицензий моделей.

## Практика

### Пайплайн (реализован)
```
chunks.jsonl ──► BM25Okapi (rank_bm25) ──┐
                                          ├──► RRF (k=60, руками) ──► топ-20 ──► CrossEncoder ──► топ-3 ──► LLM
index.jsonl ──► dense (e5-small, готовые │
вектора 384d, запрос через encode_query)─┘
```
- Dense: `intfloat/multilingual-e5-small` (вектора из index.jsonl, корпус не переэмбеддится; запрос — `encode_query`).
- Sparse: `rank_bm25.BM25Okapi`, токенизация `re.findall(r"\w+", text.lower())`.
- RRF: `score[id] += 1/(60 + rank)` по обоим спискам id.
- Реранкеры: `BAAI/bge-reranker-base` → заменён на `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`.

### Результаты эксперимента (6 запросов + 3 мусорных)
- Ответы 6/6 правильные, с источниками (`source`, `page`).
- **Реранкер исправил топ-1 в 4 из 6 запросов** — RRF шумит в верхушке, кросс-энкодер чистит.
- Мусорные запросы (борщ, чемпионат мира, карбюратор) корректно отброшены.

### Наблюдение: RRF наказывает одиночное лидерство
k=60 сплющивает вклады: документ «1-й в одном списке, 25-й в другом» (1/61 + 0) проигрывает документу «3-й и 10-й» (1/63 + 1/70). RRF поощряет консенсус → без реранкера верхушка шумная. Это норма, а не баг.

### Баг токенизации (важный урок)
`lower().split()` склеивал знак вопроса: `crispr-cas9?` ≠ `crispr-cas9` → BM25 промахнулся на точном термине (топ-1 = астрономия). Лечение: regex-токенизация **и для корпуса, и для запроса** (одна и та же!).

### Калибровка реранкера
- Скоры кросс-энкодеров — **логиты**, не вероятности. Порог «на глаз» (0.35) зарезал 4 правильных ответа.
- `bge-reranker-base` на русском: шкала сжата в 0.0–0.7, релевантное и мусор пересекаются → заменён.
- `mmarco-mMiniLMv2`: шкала −7…+4.5. Но края всё равно пересекаются (правильный −4.35 < мусорный −4.16) → на малых выборках идеального порога нет; порог подбирается под распределение конкретной модели и корпуса.

## Выводы дня

1. Пайплайн dense + BM25 → RRF → реранкинг работает; каждая стадия исправляет свою ошибку: retrieval даёт кандидатов, RRF сливает несопоставимые шкалы в один список, реранкер возвращает потерянную «уверенность» и читает текст целиком.
2. RRF поощряет консенсус и может топить одиночное лидерство — поэтому реранкинг обязателен поверх.
3. Токенизация определяет качество BM25: один приклеенный «?» = промах на точном термине.
4. Скоры кросс-энкодеров — логиты разных шкал у разных моделей; порог — только эмпирическая калибровка.
5. Русскоязычный корпус → мультиязычные модели на каждой стадии (e5-small ✓, mmarco ✓, bge-reranker-base ✗).
6. Самая слабая стадия в моём пайплайне оказалась не retrieval и не слияние, а кросс-энкодер не на своём языке — качество каждой стадии измеряется отдельно.
7. Contextual Retrieval (контекст к чанкам до индексации) — следующий апгрейд «на вырост»: −49% промахов, не требует переделки пайплайна.
